## Problem

The guide introduces the route map, route builders, and controller ownership, but this app relies on parts the guide only mentions in passing (resource `exclude`, any-method leaves, nested-map registration), and the failure modes are easy to misread. A missing action does not fail on the first request; a controller cannot reach nested maps; `context.headers` is not a response-header channel. Copying the guide examples verbatim (`only`, `param`) produces a route contract that does not match the app.

## Solution

### Resource helpers: the app uses `exclude`, the guide shows `only`

- Guide §"Route builders: route, get, post, put, del, form, resources" documents `only` and `param`. `resources()`/`resource()` also accept `exclude` (the complement of `only`) and `names`; `only` and `exclude` are mutually exclusive, enforced at the type level (`only?: never`) and at runtime (`Cannot specify both "only" and "exclude" options`). See `node_modules/remix/src/fetch-router/README.md` §"Resource-based Routes" and the installed `route-helpers/resources.ts` / `route-helpers/resource.ts`.
- This app still uses `exclude` for the generated resources: `app/routes.ts:313` (`verwaltung.resources` = `exclude: ['new', 'edit']` → index/show/create/update/destroy) and `app/routes.ts:315` (`verwaltung.offeringConfigs`). `appointment.types` is now an explicit route map at `app/routes.ts:92` (`index`/`create`/`update`/`destroy`) because `resources()` hardcodes `PUT` for `update` (`route-helpers/resources.d.ts`: `update: { method: 'PUT'; pattern: '/:id' }`); the explicit map lets `update` be PATCH without changing the other leaves. If you add a resource, keep the `exclude` spelling so the generated leaves stay consistent with the sibling routes; do not convert to `only` just because the guide uses it.
- Generated leaf names are conventional (`index`, `new`, `show`, `create`, `edit`, `update`, `destroy`) unless `names` renames them, and the path variable defaults to `id` unless `param` changes it. This app passes neither for these maps.
- `appointment.types` is its own nested route map, so it has its own doctor entry point (`app/actions/appointment/types/controller.tsx`, a re-export of `appointmentTypes` in `app/actions/appointment/controller.tsx:458`) and its own `router.map(routes.appointment.types, appointmentTypes)`. It is hand-written rather than generated by `resources()`, but the leaf names and doctor/controller wiring are unchanged.

### `patch`, `head`, `options`, and bare-string (any-method) leaves

- Guide §"Route builders: route, get, post, put, del, form, resources" lists the method builders; `patch`, `head`, and `options` are exported from `remix/routes` exactly like `get`/`post` (`route-helpers/method.ts`). This app imports `patch` at `app/routes.ts:1`; the PATCH leaves are `routes.lists.update` (`app/routes.ts:42`), `routes.appointment.update` (`:89`), and `routes.appointment.types.update` (`:95`). `head`/`options` remain unused; adding one is still a new import from `remix/routes`.
- `head` interacts with `GET`: a `GET` route also serves `HEAD`, and an explicit `HEAD` route wins for `HEAD` (`node_modules/remix/src/fetch-router/README.md` §"HEAD Requests"). Since #12190 the fallback is picked while resolving the route (the most specific `GET` match, installed `fetch-router/src/lib/router.ts:478-526` in `resolveFromMatchAll()` / `:555-601` in `resolveRoute()`; #12448 added the exact-static fast path ahead of this resolver while preserving the same HEAD/405 fallbacks), and the body is stripped **after** router middleware returns: `dispatchWithRouterMiddleware()` awaits `runMiddleware(...)` and only then passes the response through `headResponse()` (`:635-671`, and for direct dispatch `finalizeDirectResult()` at `:414-434`), which cancels the GET body and returns `new Response(null, { status, statusText, headers })` (`:259-271`). Ordering rule: router middleware sees the **GET** response (its status and headers), and any header it adds survives on the `HEAD` response; only the body is dropped. Do not move header stamping into the route handler for HEAD — put it in router middleware, after `next()`. This app registers no `HEAD` leaves and relies on the fallback; `app/actions/home/controller.test.ts` §"HEAD requests served by the GET fallback" guards `HEAD /` and `HEAD /health` (GET status, all stable headers, empty body, and exactly one middleware pass via the first logger).
- A bare-string leaf (`webhook: "/webhooks/github"`, guide §"Route builders: route, get, post, put, del, form, resources") produces a `Route<'ANY', ...>` that matches any method, so its action must branch on `context.method`. This app has no `ANY` leaf today: the webhook/callback endpoints are `post(...)` (`app/routes.ts` `system.*`, mapped with `router.post(...)` in `app/router.ts`). If you add an `ANY` leaf, `context.method` is the field to switch on — the same field `app/middleware/uploads.ts:125` reads (`context.method === 'POST'`).

### Mutation method taxonomy: PATCH vs PUT vs POST

- **PATCH — partial payload.** `routes.lists.update` (the `/lists` editor autosave, keepalive flush, and inline rename; `listsPatchSchema` is all-optional with an explicit "at least one of title/description/items" check and `patchList` applies only present fields under `If-Match`), `routes.appointment.update` (the client appointment grid's title/slot writes; `appointmentUpdateSchema` is all-optional and the handler merges omitted slot bounds with the stored row), and `routes.appointment.types.update` (rename; only `title` is optional).
- **PUT — full editable representation.** Admin clients/users/lists, offerings, verwaltung appointments, generated `resources`/`offering-configs`, and `/api/lists/:id` (description and items are required). Do not convert these for consistency: PUT's contract is a full replacement, and the payloads really are complete forms.
- **POST — commands/actions.** The client status/user-disabled row toggles, lists move/copy/merge/delete, notifications mark-read, page-size, resend, and chat/agent actions. These are operations, not partial resource representations.
- **`resources()` hardcodes PUT for `update`.** The generated `update` leaf is `{ method: 'PUT'; pattern: '/:id' }` (`route-helpers/resources.d.ts`), so a PATCH conversion of a generated resource must replace the helper with an explicit `route(...)` map that preserves `index`/`create`/`update`/`destroy` (as done for `appointment.types` at `app/routes.ts:92`). There is no resource option that changes the method.
- **Method plumbing.** `RestfulForm` supports any method and emits `_method=PATCH`; `methodOverride()` and CSRF already accept it. Direct client fetches send the real PATCH with `X-Csrf-Token`. `navigator.sendBeacon` cannot send PATCH, so the lists keepalive flush stays `fetch(..., { keepalive: true })` (`app/actions/lists/public/lists-api.ts:256-270`).
- **Conversion checklist.** Change the route helper and every client fetch method; update server tests, browser/e2e method assertions (`init.method`, `waitForResponse`, and the appointment fetch-capture helper), and the learned references. Keep the `GET /:id` action-path resolvers and frame routing unchanged — only the HTTP method changes.

### Idempotent row actions: submit the desired state, not a toggle

- A row action that flips current state (status active/inactive, user disabled/enabled) is not retry-safe: a POST that commits but loses its response, or a double submit, re-reads the new state and flips it back. Submit the **promised target state** in a hidden field instead (`desired_status` / `desired_disabled`), apply that target in the handler, and no-op when the row is already there.
- On the no-op path, skip the DB write, audit entry, and `token_version` bump. Keep the old flip behavior when the field is absent (stale pre-deploy forms), and fail an explicit but invalid target with a flash error rather than silently falling back.
- App anchors: `app/actions/client/controller.tsx` (`toggleStatus`), `app/actions/client/grid-page.tsx` (`desired_status`), `app/actions/admin/users/controller.tsx` (`toggleDisabled`), `app/ui/admin-users-page.tsx` (`desired_disabled`); idempotency tests live in `app/actions/client/controller.test.ts` and `app/actions/admin/admin-users.test.ts`.

### A controller owns only its direct leaves; nested maps are registered separately

- Guide §"Mapping controllers". `router.map(routeMap, controller)` walks only the direct `Route` leaves of `routeMap`; a nested map key is never auto-registered and needs its own `router.map(nestedMap, nestedController)` call.
- This app follows that rule: the root map controller owns only `assets`/`home` (`app/actions/controller.tsx` re-exports `app/actions/home/controller.tsx`), while each branch (`routes.lists`, `routes.appointment`, `routes.appointment.types`, each `routes.verwaltung.*`) is mapped separately in `app/router.ts:55-150`. The clearest example is `app/router.ts:118-119`: `routes.appointment` and `routes.appointment.types` are two controllers (`appointment`, `appointmentTypes`) for two maps.
- `router.map(...)` validates at registration, not on the first request. A missing direct leaf throws `TypeError: Missing action <key> in controller`; a nested map key placed inside `actions` throws `Cannot map nested route map key <key> in controller actions; call router.map() for that route map separately`; an unknown key throws `Unknown action <key> in controller` (installed `fetch-router/src/lib/router.ts` (`mapController`)). In this app the calls run inside `createNewappRouter()` (`app/router.ts`), which `server.ts` invokes at module eval and tests use via `app/test-router.ts`, so the failure surfaces at import/startup — the setup-time throw guide §"Mapping controllers" describes.

### Controller middleware does not flow into nested route maps

- Guide §"Mapping controllers". `controller.middleware` is merged into each direct leaf registered from that controller (installed `fetch-router/src/lib/router.ts` (`mergeMiddleware` in `mapController`)); it is not inherited by a nested map mapped separately. If a nested branch needs the same boundary, put the middleware on that branch controller or share the middleware array.
- App seam: `routes.lists` and `routes.appointment` each declare `middleware: [requireAuth()]` on their own controller (`app/actions/lists/controller.tsx:122`, `app/actions/appointment/controller.tsx:122`), and the nested `appointment.types` controller repeats `requireAuth()` (`app/actions/appointment/controller.tsx:459`). The `requireAuth` on `routes.appointment` does not cover `routes.appointment.types`; the repetition is required, not redundant. The same pattern holds for the admin boundary on `routes.verwaltung.resources` (`app/actions/verwaltung/resources/controller.tsx:189`).

### Built-in action context: `has`, `router`, and the request-only `headers`

- `context.has(key)` returns whether a value was stored for a context key; it checks the context map only, so a key with a `defaultValue` reads `false` from `has` while `get` returns the default. Use it to detect whether an earlier middleware actually ran. There is no current app caller (grep `context.has(` under `app/` is empty); the context-key work is in `references/context-keys-and-dependency-flow.md`.
- `context.router` (guide §"Controllers and actions") is the router handling the request; the getter throws `No router found in request context.` when unset. It is the seam for re-entering the pipeline from middleware: `app/middleware/frame-redirect.ts:94-107` calls `context.router.fetch(followRequest)` (signal at `:97`) to follow an in-frame redirect. That internal fetch bypasses `createRequestListener` (no client address, no `onError`), so anything the server boundary injects (such as `X-Client-Ip`) must be forwarded explicitly — as that call does for the `Cookie` header.
- `context.headers` is a mutable copy of the request headers (guide §"Controllers and actions"); guide §"Responses, redirects, headers, and errors" states that it is not the response headers and that controllers have no response-header API — return a `Response` and set its headers. App seam: `app/middleware/frame-redirect.ts` reads request headers from `context.request.headers`, builds request headers into a `Request`, and writes response headers with `frameResponse.headers.set(...)` on the returned `Response`. Do not look for a `context.response` or a context header setter.

### Route params are strings — guard id-shaped params before SQL

- Guide §"Controllers and actions": route matching guarantees the param exists and is typed as a `string`; it does not guarantee a number. `:id` matches `abc`, `1.5`, and `1e30` just as readily as `42`, and a raw value handed to an `int4` comparison makes PostgreSQL throw (`Database execution failed`), which surfaces as a 500.
- App convention (landed in the 2026-11-14 §02 re-audit): `parseId(context.params.id)` (safe-integer parse, so `1.5`/`1e30` fail) then a `< 1` bound check before any id query. Mutations flash `Ungültige ID.` and PRG (`303`) back to the grid; GET `show` resolvers redirect to the grid, matching their missing-row branch.
- Match the expected-failure representation to the request (2026-11-28 §12 audit). A document/native-form or `X-Remix-Frame` request needs the HTML page/fragment; a JSON 4xx inside a frame is a non-HTML body, so the app's resolver replaces it with the generic recovery card. `app/actions/admin/users/controller.tsx` now uses `isPageRequest()` (frame or document) to re-render the 403 grid fragment and to flash + PRG missing/invalid update/delete ids, while API/bare-`fetch` clients keep JSON. Do not let a missing row fall through to `updateMany` (0 rows) and redirect as success.
- Fixed seams: `app/actions/verwaltung/resources/controller.tsx:205` (show), `app/actions/verwaltung/offering-configs/controller.tsx:360` (show), `app/actions/verwaltung/appointments/controller.tsx:311` (show), `:468` (update), `:625` (destroy), `app/actions/verwaltung/offerings/controller.tsx:340` (update), `:447` (destroy), and `app/actions/appointments-new/controller.tsx:593` (destroy). `app/actions/verwaltung/resources/controller.tsx:323`/`:383` already had it and are the template.
- The raw-SQL helpers still take the id as a `string` (`fetchAppointmentEditRow`, `updateOffering`, `deleteOffering`, `getAppointmentRow`, `adminUpdateAppointment`, `adminDeleteAppointment`), so pass the original validated string, not `Number(...)`; `parseId` is the guard, not the value conversion. Tests cover each seam with a non-numeric id.

### Probe route-param robustness through the test router

Green suites exercise valid ids only, so a `/:id` leaf can 500 on malformed input for months.
Probe every id leaf with a throwaway server test (`tmp/` is gitignored; imports resolve to
`../app/...`):

```ts
import { test } from 'remix/test'
import { router } from '../app/test-router.ts'
import { createAuthCookieWithCsrf } from '../test/utils.ts'
import { routes } from '../app/routes.ts'

test('probe malformed route ids', async () => {
  let session = await createAuthCookieWithCsrf()
  // Build each path through the route tree so a route rename cannot turn this
  // probe into a 404 false negative; only the :id value is deliberately bad.
  let paths = [
    routes.verwaltung.resources.show.href({ id: 'abc' }),
    routes.verwaltung.offeringConfigs.show.href({ id: 'abc' }),
    routes.verwaltung.appointments.show.href({ id: 'abc' }),
  ]
  for (let path of paths) {
    try {
      let response = await router.fetch('https://remix.run' + path, {
        headers: { Cookie: session!.cookie },
        redirect: 'manual',
      })
      console.log(path, '->', response.status)
      await response.text()
    } catch (error) {
      console.log(path, '-> THREW', (error as Error).message)
    }
  }
})
```

Run `NODE_ENV=test npx remix test --type server --concurrency 1 tmp/probe-route-ids.test.ts`.
`THREW Database execution failed` is the int4 failure the `parseId` guard prevents. For
`PUT`/`DELETE` leaves send the real method plus `X-Csrf-Token: session.csrfToken` (no `_method`
override when calling `router.fetch` directly). Turn each confirmed throw into a regression test
next to its controller, then delete the probe. Audit-workflow context:
`docs/guide-chapter-audit.md` §3.

### `RoutePattern` is opaque — use the public API

Do not read pattern internals (`route.pattern._parts`, `route.pattern.pathname.tokens`, `route.pattern.hostname.tokens`). Use the public surface documented in `node_modules/remix/src/route-pattern/README.md`:

- `route.pattern.source` / `toString()` — normalized pattern string
- `route.pattern.toJSON()` — serialized `protocol`/`hostname`/`port`/`pathname`/`search` parts
- `getRoutePatternCaptures(route.pattern)` — `{ part, type, name, optional }[]` for variables/wildcards, in source order

The app's `routeParentPath()` (`app/route-labels.ts`) derives a parent path without token walking:

```ts
function routeParentPath(route: { pattern: { source: string } }): string {
  return route.pattern.source.replace(/\/[:*][^/]*$/, '/')
}
```

## When to Use

- Adding or reshaping a CRUD route with `resources()`/`resource()` and deciding `only` vs `exclude` in this app.
- Registering a controller for a route map whose branches are handled by their own controllers, or triaging a `Missing action` / `nested route map key` / `Unknown action` throw at startup.
- Adding a `patch`/`head`/`options` leaf, an any-method (bare-string) route whose handler must check `context.method`, or a `HEAD` request served by the `GET` fallback (body stripped after router middleware; middleware sees the GET response). The app's PATCH leaves are partial updates; full forms stay PUT and commands stay POST.
- Converting a partial PUT endpoint to PATCH (`resources()` hardcodes PUT for generated resources), or hardening a retrying row action so it submits the desired state and no-ops when already current.
- Reading `context.has`, `context.router`, or `context.headers` inside middleware/actions and expecting response-side behavior from `context.headers`.
- A `RoutePattern` property stops typechecking, or you need a route's variables/wildcards (`getRoutePatternCaptures()` replaces token walking; `routeParentPath()` shows the string-based parent-path rewrite).
