## Problem

Guide 03 describes the portable path and the middleware contract, but this app assembles its own root chain in `app/middleware/root.ts` and its own boundary behavior in `server.ts`, `server.bun.ts`, and `app/utils/server-handler.ts`. Error handling has moved to `createRequestListener({ onError })`, and the app derives `AppContext` from a stored chain rather than the guide's inline `RouterContext<typeof router>`. This reference records those seams and the ordering rules the app depends on.

## Solution

### `createRequestListener` options: `host`, `protocol`, `onError`

- Guide §"createRequestListener". `host` and `protocol` pin the values used to build `request.url`; `trustProxy` trusts `Forwarded`/`X-Forwarded-*` (covered by `security-gotchas`); `onError(error)` logs and may return the response sent instead of the default `500`. When `host` or `protocol` is set, it takes precedence over trusted proxy headers (`node_modules/remix/src/node-fetch-server/README.md`).
- App seam: `server.ts:33-42` calls `createRequestListener((request, client) => handleRequest(request, client.address), { trustProxy: isHmr, onError(error) { console.error(error); return renderServerError() } })`. `onError` is the Node boundary's 500 path; `createServerHandler` (`app/utils/server-handler.ts:92-100`) only stamps `X-Client-Ip` and calls `router.fetch` — it does **not** catch. `server.bun.ts` catches its own async rejection because it bypasses `createRequestListener`. `trustProxy` is `true` only for the HMR dev proxy, never in production.

  `host` and `protocol` are intentionally unset: production serves TLS directly (`https.createServer`) and derives external links from `PUBLIC_ORIGIN` rather than the request Host; the dev HMR child is the only `trustProxy: true` caller and binds `127.0.0.1` (`hmr.ts`). Do not enable `trustProxy` in production without a reverse proxy that overwrites `Forwarded`/`X-Forwarded-*`, or a client can spoof the protocol/host/address the app sees.

### The `(request, client)` second argument and the low-level exports

- Guide §"createRequestListener". The handler receives `client: ClientAddress` with `address`, `family` (`IPv4` | `IPv6`), and `port` (installed `node-fetch-server/src/lib/fetch-handler.ts`).
- App seam: `server.ts` imports `type ClientAddress` and uses only `client.address`; `createServerHandler` stamps it as `X-Client-Ip` before `router.fetch` (`app/utils/server-handler.ts`), which `app/utils/request-ip.ts` (`connectionIp`, `sourceIp`) and the rate limiter read. `server.bun.ts` mirrors the same contract from Bun's `runtime.requestIP(request)?.address` because it never goes through `createRequestListener`. If you add client-address-dependent middleware, consume `X-Client-Ip` (the boundary already set it) rather than re-deriving it from arbitrary headers.
- The same package also exports the low-level `createRequest(req, res, options)` and `sendResponse(res, response)` (node-fetch-server README, "Low-level API"). This app has no caller (grep `createRequest(`/`sendResponse(` is empty) and no reason to add one: `createRequestListener` already covers the flow, and the app needs the URL construction and `onError` behavior that live in `server.ts`.

### `compression()`: negotiation, guards, and the before-`staticFiles()` rule

- Guide §"Middleware ordering" and §"Common middleware: form-data, render, static files, compression, logging" state the ordering rule: a response wrapper must run before the early response it should wrap, so `compression()` must precede `staticFiles()`. The middleware negotiates `br`, `gzip`, `deflate` from `Accept-Encoding` and skips already-compressed responses, responses that advertise range support (`Accept-Ranges: bytes`), non-compressible MIME types, and bodies below the threshold (default 1024 bytes, enforced only when `Content-Length` is present) — see `node_modules/remix/src/compression-middleware/README.md`.
- App seam: the root chain follows the guide — `securityHeaders()` → `csp()` → `compression()` → `staticFiles('./public', { index: false, cacheControl: … })` (`app/middleware/root.ts:63-90`). The vendor `csp()` sits between them so static responses still get the policy/nonce; `securityHeaders()` owns the non-CSP hardening headers and cache policy. Consequences: static responses are wrapped by `securityHeaders()`, `csp()`, and `compression()`; `.woff2` files are skipped by the already-compressed MIME guard, and `fonts.css` is text but at ~495 bytes it is below the default 1024-byte threshold, so the current file is **not** actually compressed. Raise the file above the threshold or pass `compression({ threshold })` before relying on compressing it. Requests that reach actions are also wrapped, because `compression()` sits before the session/database/render stack. Keep `compression()` above `staticFiles()` if you add large static text. The app uses the default compression options; `app/middleware/compression.test.ts` proves a real HTML response comes back `Content-Encoding: gzip` and gunzips to the document.

### `logger()` and `context.logger(...)`

- Guide §"Common middleware: form-data, render, static files, compression, logging": `logger()` logs the request and downstream response and provides `context.logger(...)`; put it first so early responses and `404`s are logged. The logger README documents the token `format` option, `colors`, a custom `log`, and `context.get(Logger)`.
- App seam: the app does not use a bare `logger()` first. `app/middleware/root.ts:41-59` defines `skipAssetsLogger()`, a `Middleware<{ key: typeof Logger; value: LoggerFunction; property: 'logger' }>` that delegates to `logger({ format: '[%date] %method %path → %status (%duration)' })` for non-asset paths, and for `/assets/` installs `context.set(Logger, console.log, { property: 'logger' })` and only logs responses with status >= 400. It is first in the chain (`app/middleware/root.ts:63`), so the log-early-responses rule holds.
- `context.logger?.(...)` is this app's standard failure logging in controllers (about twenty calls, e.g. `app/actions/lists/controller.tsx:319`, `app/actions/auth/controller.tsx:287`). Use the optional call in controllers rather than `console.error` so the configured format is reused; the property comes from the logger middleware installed by `skipAssetsLogger()`.

### Middleware scopes and ordering rules

- Guide §"Middleware ordering". Three scopes: router middleware (before route matching, every request), controller middleware (direct actions of one controller), and action middleware (one action); the full order is router, then controller, then action, then handler. Choose order by dependency and wrapping: provider before consumer, response-wrapper before the early response it wraps, work after a fast path that does not need it.
- App chain: `createNewappMiddleware(cookie, storage)` in `app/middleware/root.ts:61-136` is the single router middleware tuple, built with `createMiddleware(...)` so its type survives. Order-dependent pairs the app relies on:
  - `securityHeaders()` before `csp()`, `compression()`, and `staticFiles()` so static responses still carry the hardening headers and the CSP (`:63`–`:90`). `csp()` must come after `securityHeaders()` (it owns the nonce/policy) and before `compression()`/`staticFiles()` so those responses are stamped.
  - `session(cookie, storage)` before `asyncContext()`, `loadDatabase()`, `loadAuth()`, and `skipCsrf()` (`:105`–`:122`).
  - `loadDatabase()` before `loadAuth()` (`:111` vs `:112`); `loadAuth` calls `context.get(databaseContext)` and throws `Expected database middleware before session auth scheme` if the DB was not set first (`app/middleware/auth.ts`).
  - `uploadClaimScope()`/`uploadFilesScope()` before `uploadFormData()` (`:114`/`:118` vs `:119`), and `uploadFormData()` before `methodOverride()` (`:120`), matching guide §"Common middleware: form-data, render, static files, compression, logging".
  - `methodOverride()` before `jsonBody()` and `skipCsrf()`; `skipCsrf()` must stay after `uploadFormData()` because `csrf()` reads the token from `context.get(FormData)`. The upload middleware itself performs pre-parse 401/403 checks because auth and request context now run earlier (`:105`–`:119`).
  - `asyncContext()` before any middleware that reads ambient context (`getContext()`), including `loadAuth`/`uploadFormData`.
  - `loadAssetEntry()` after CSRF and before `render({ assets: assetServer })`; `render` follows middleware that may answer without rendering (`:123` vs `:128`).
- Controller- and action-scope details are in `references/route-contract-and-controllers.md`: `createController(..., { middleware })` merges only into direct leaves, and the per-action object form is `{ middleware, handler }`.
- Controller middleware does **not** flow into a controller mapped for a nested route map. `app/router.ts` maps each nested map separately, and every guarded subcontroller carries its own guard (e.g. `routes.admin.chatlog.fragments` → `adminChatlogFragments` with `[requireAuth(), requireAdmin()]`, and `routes.admin.webhookRequests.events` → `adminWebhookRequestsEvents` with `[requireAdminSseAuth()]`). Do not move a guard to a parent map and assume nested leaves inherit it.

### `RouterContext<typeof router>` vs this app's `MiddlewareContext` factory

- Guide §"Typed request context" shows `type AppContext = RouterContext<typeof router>` followed by `declare module "remix" { interface RouterTypes { context: AppContext } }`, which works when the middleware chain is an inline array on the `createRouter(...)` call. The same section splits the cases: inline arrays use `RouterContext`; a reusable or stored chain uses `createMiddleware(...)` plus `MiddlewareContext<typeof middleware>` (also `node_modules/remix/src/fetch-router/README.md` §"Typed Context Contracts").
- App seam: this app stores the chain in a factory, so `AppContext = MiddlewareContext<ReturnType<typeof createNewappMiddleware>>` (`app/types/context.ts`), and `app/router.ts` still performs the module augmentation (`declare module 'remix' { interface RouterTypes { context: AppContext } }`). Do not simplify to `RouterContext<typeof router>` without inlining the whole chain: the factory split is what keeps `app/types/context.ts` from importing `router.ts` and closing the `router.ts → controllers → context.ts → router.ts` cycle documented in `references/context-keys-and-dependency-flow.md`. Apps with multiple routers should pass explicit context types instead of the app-wide default (guide §"Typed request context"); this app has one router factory and relies on the global augmentation.

### `request.body` / `ReadableStream` and `request.signal`

- Guide §"The Web Request/Response contract": bodies stay Web streams, actions can read `request.body`, return a `Response` backed by a `ReadableStream`, and observe cancellation through `request.signal`.
- App seams:
  - Stream body with a cap: `app/middleware/json-body.ts` reads `context.request.body?.getReader()`, accumulates chunks, and calls `reader.cancel()` when the byte cap would be exceeded (chunked or unknown-length requests); it uses `Content-Length`/`Transfer-Encoding` to choose the cheap path.
  - Cancellation: `app/utils/sse.ts:136` registers `request.signal.addEventListener('abort', ...)` to drop the subscriber and close the stream when the client disconnects; `app/actions/agent-events/controller.tsx:317` checks the stream scope's `signal.aborted` inside a stream loop; `app/middleware/frame-redirect.ts:94-107` forwards `signal: context.request.signal` into the internal `context.router.fetch`.
  - **A cancelled response body is a second cleanup path, not only an abort.** Since remix #12190 `remix/fetch-router` cancels the body of a response that nothing will read after an abort; #12446 replaced the old racing (`raceRequestAbort()`/`AbortRace`) with cooperative boundary checks: `throwIfRequestAborted()` (`fetch-router/src/lib/request-abort.ts:12-19`) cancels a concrete unread/late `Response` and throws the abort reason, while `getRejectionReason()` (`:29-31`) prefers the abort reason over the work's own error. #12447 removed the old Promise-body follower (`cancelUnreadResponse()`): direct `return next()`, async no-return, and synchronous-return middleware now take the `signal.aborted ? settleAndCheckAbort(nextPromise) : nextPromise` path in `runMiddleware()` (`middleware.ts:181-215`; helper at `:120-131`), so the router waits for downstream work before rejecting. `runMiddleware()` spans `middleware.ts:112-223` and checks before each layer and when work settles (`:137`, `:143`, `:177`, `:195`, `:201`, `:214`); `finalizeDirectResult()` does the same for the direct handler (`router.ts:414-434`). `createRequestListener` cancels the response reader when the HTTP response closes (`RequestLifecycle` stores it in `node-fetch-server/src/lib/request-listener.ts:941` and cancels it in `node-fetch-server/src/lib/request-abort.ts:28-29`). A server `ReadableStream` needs an underlying `cancel()` hook for this: `createAbortScope()` (`app/utils/agent-sse.ts:80`) links the request signal to a stream-local controller whose `abort()`/`cleanup()` are idempotent, and `createRunSignal()` (`:121`) adds the whole-run timeout and the same `abort()`. The app wires it into every SSE source: `app/utils/sse.ts:146` (heartbeat + subscriber), `app/utils/agent-sse.ts:160` (`sseRunResponse()`, which all six chat streams in `app/utils/agent-chat.ts` and `app/utils/agent-chat-durable.ts` open through, so the hook cannot be forgotten — abort the agent run, clear the timeout/listener; a cancelled durable stream must not record an ownership row), and `app/actions/agent-events/controller.tsx:449,540` (abort the workflow/bus scope). `cancel()` must tolerate a racing abort: closing an already-cancelled controller throws (use `safeClose`) and a second `clearInterval`/`removeEventListener` must be harmless. Guards: `app/utils/sse.test.ts`, `app/utils/agent-sse.test.ts`, `app/utils/agent-chat-cancel.test.ts`, `app/actions/agent-events/controller.test.ts`.
  - Use `context.request.signal` (the original request), not a fresh `AbortController`, for disconnect-driven cleanup. An abort during a handler surfaces as a `router.fetch` rejection whose reason is the signal reason (since #12446, once the handler settles — the router no longer races it, so pass the signal into the work that should stop). `server.bun.ts`'s `fetch` catch suppresses logging for exactly `request.signal.aborted && error === request.signal.reason`. The Node listener needs no equivalent: its two-argument branch returns before `onError` when `isRequestAbortError(request, error)` (installed `request-listener.ts:185`), and `sendResponseForRequest` skips a response whose request aborted (`:244`). So an abort during the handler does not reach `onError` in either entry; the Bun suppression only covers a runtime that bypasses `createRequestListener`.
  - **Request deadline:** `app/middleware/request-timeout.ts` (root chain, after `globalRateLimit` and before `session`) is opt-in via `REQUEST_TIMEOUT_MS`. It replaces `context.request` with `AbortSignal.any([request.signal, timeout])`, races `next()` against the deadline (504 + cancels a late body), and skips SSE (`Accept: text/event-stream` or `X-Sse-Request: 1`). Keep deadlines in middleware — since #12446 the router no longer races layers against the signal, so downstream work must observe it to stop. The Hermes sends (`app/actions/admin/webhook-requests/controller.tsx`, `app/actions/app-webhook/controller.tsx`) combine their 3 s timeout with `context.request.signal` and record `aborted` rather than `error` when the caller disconnects.
  - **Raw SQL reads get the request signal through an `AsyncLocalStorage` scope.** `queryAbortScope()` in the root chain runs immediately after `requestTimeout()`, so it stores the combined client/deadline signal (`context.request.signal`) rather than only the original request signal. `queryRows()`/`queryRow()` read that signal and call `throwIfAborted()` before `db.exec()` and again after the query settles. The helper must not race the query promise: `@remix-run/data-table-postgres` exposes no query-cancellation hook, and rejecting a wrapped query inside `db.transaction()` could let rollback run on the same client while the query is still executing. The checkpoints keep transaction commands ordered; the already-started query remains bounded by the pool's `statement_timeout: 30000`. Direct `db.exec()` calls are not automatic — use `queryRows`/`queryRow` for abort-aware reads, or pass `{ signal }` explicitly outside a request. Guards: `app/data/rows.test.ts` proves the first read starts, the abort rejects once it settles, and a second read never starts; `app/middleware/query-abort.test.ts` proves the scope reaches a router handler; `app/middleware/request-timeout.test.ts` pins the router-level "cleanup completes before rejection" ordering.

## When to Use

- Editing `server.ts`, `server.bun.ts`, or `app/utils/server-handler.ts`: host/protocol, the `(request, client)` client address, or where the 500 response is produced.
- Changing the root middleware order in `app/middleware/root.ts`, especially `compression()` vs `staticFiles()`, or adding a provider/consumer pair.
- Reading `context.logger` in a controller, or wiring and altering the logger.
- Deriving or augmenting `AppContext` and deciding between `RouterContext` and `MiddlewareContext`.
- Handling a streaming response or client disconnects through `request.body` / `request.signal`, or returning a server `ReadableStream` (SSE): add a `cancel()` hook that aborts the producer and clears timers/listeners, and prove it by cancelling the response body in a test (aborting the request alone does not exercise `cancel()`).
- Adding or changing raw database reads: use `queryRows()`/`queryRow()` so the request's abort signal refuses new reads and rejects after the in-flight query settles. Do not add a `Promise.race(query, abort)` wrapper around a driver that cannot cancel the query, and keep `queryAbortScope()` after `requestTimeout()`.
