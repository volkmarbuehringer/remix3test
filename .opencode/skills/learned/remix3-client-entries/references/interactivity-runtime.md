# Remix 3 Interactivity Runtime

**Source:** Installed guide `node_modules/remix/guides/05-interactivity.md` (remix 3.0.0-rc.3); line refs in the text below are to that file. App seams verified against `app/`.

**Extracted:** 2026-09-26

**Context:** Wiring browser interactivity in a Remix 3 `clientEntry`: a client-only root, the `run()` runtime lifecycle, custom event mixins, cancellation granularity, optimistic/pending ownership, `navigate`/`link`/`attrs`, list keys and input ownership, and enhanced form submission. This reference points at the guide and records only the app-specific seams and disambiguations the guide cannot know.

## Problem

The guide covers the runtime and mixin APIs completely, but this app has its own client wiring (`app/assets/entry.tsx`, `app/assets/error-card.browser.tsx`) and its own shared handler conventions that diverge from the guide's examples in ways that are easy to misread: `createRoot` is used for a fatal-error takeover rather than a widget; `navigate` is shadowed by a local frame-navigation helper in one file; the existing form interception is the SSE/JSON stream path, not the guide's fetch-and-redirect enhancement; and no app code uses the `on(...)` per-handler signal, `createMixin`, `link()`, or `attrs()`. Treating any of these as "already implemented like the guide" leads to wrong edits.

## Solution

**Client-only root — `createRoot(container)` (guide L169-195)**

- The root owns its container. `root.render(node)` schedules a tree, `root.flush()` applies pending work synchronously, and `root.dispose()` removes the tree and runs cleanup; the guide's widget example disposes on `pagehide` with `{ once: true }` (L184-189). Reserve `createRoot` for UI with no server-rendered component to hydrate; normal page UI starts on the server via `clientEntry(...)` so users are not left waiting on JavaScript (L192-195).
- App seam: the only `createRoot` in the app is the fatal-error takeover — `renderFatalError()` in `app/assets/error-card.browser.tsx:113-135` calls `createRoot(document.body).render(<ErrorCard .../>)`. It runs from `run()`'s error listener (`app/assets/entry.tsx:44-56`) **after** `app.dispose()` and after `fadeOutBody()` clears `document.body`, so the root replaces the whole document. It never registers the guide's `pagehide` dispose (the runtime it could outlive is already gone) and never calls `root.flush()`/`root.dispose()` itself. A future non-fatal client-only root (a widget in a page shell) is new behavior: copy the guide's `pagehide` dispose, not the error card's terminal pattern.

**Browser runtime lifecycle — `run()` (guide L156-161)**

- `app.ready()` resolves after the initial client entries hydrate. `app.flush()` synchronously applies pending component updates — the supported way to observe the DOM immediately, scoped by the guide to tests and integrations. `app.dispose()` removes the runtime's components and listeners (L158-161).
- App seam: `app/assets/entry.tsx:11-12` keeps the `run()` result in module `app`, but nothing in `app/` calls `app.ready()` or `app.flush()` (verified). The single lifecycle call is `app.dispose()` in the error listener at `:44-45`, immediately before the error card mounts. There is no production or test seam that waits on `ready()`; the app relies on `app.addEventListener('error', ...)` (`:44`) for failure handling, and `remix3-testing` owns how tests drive client DOM without `app.flush()`.

**Custom event mixin — `createMixin` + `handle.element` (guide L822-896)**

- Build the interaction from low-level events in setup scope, then dispatch one semantic typed event (`LongPressEvent extends Event` with `{ bubbles: true }`) that consumers attach with `on(...)`. `handle.addEventListener("insert"|"remove", ...)` is the **mixin handle's** own lifecycle events (not a DOM `addEventListener`): `insert` supplies `event.node`, `remove` is the cancel hook. The mixin returns `<handle.element mix={[...]} />`. Augment `HTMLElementEventMap` in a `declare global` block so the consumer's `on(longPressType, ...)` is typed, and namespace the name (`app:longpress`) to avoid collisions (L836-846, L894).
- App seam: none. `createMixin` and `handle.element` do not appear in `app/` (verified). Reusable behavior in this app is currently `on(...)` in mixin arrays plus imperative `ref` callbacks and helper modules (`app/ui/mixins/icon.ts`, `app/ui/auto-grow-textarea.ts`); no custom DOM events are dispatched outside tests, which dispatch native `submit`/`input` (e.g. `app/assets/streams/streams.test.browser.tsx:91`). A custom event mixin would be the first in the repo — follow the guide and the `remix/ui` API overview (`node_modules/remix/src/ui/README.md`), not an app precedent.

**Cancellation granularity (guide L263-277, L513-519)**

- `handle.update()` schedules work and its promise resolves to an `AbortSignal`, but the runtime **cannot** abort it between `await handle.update()` and the next synchronous statement — `input.focus()` needs no check. Capture the signal only when more async work follows: pass it to `fetch(href, { signal })` and re-check `signal.aborted` after each later `await` before touching state (L263-277). The second argument of an `on(type, (event, signal))` handler (L517) is the signal for work where the latest event should replace earlier work; it aborts on re-run **or** element removal. The `queueTask` and `handle.signal` aborts are already covered by `references/queuetask-over-raf.md` and `remix3-frame-cliententry` and are not restated here.
- App seam: no app handler uses the `on(...)` second-arg signal (verified — no `(event, signal)`/`(e, signal)` handlers). The app cancels async work with `handle.signal` on native listeners (e.g. `app/assets/streams/public/agent-events-stream.tsx:402,409-416`), a local `AbortController` (`app/actions/lists/public/list-name-edit.tsx:41-43`), or the signal returned by `handle.frame.reload()` (`app/actions/client/public/grid-refresh-button.tsx:45-50`). When you attach with native `addEventListener` — because the target is outside the render tree or you are inside a `queueTask` — you do not get the per-handler signal; pass your own controller or `handle.signal`, as those sites do.

**Pending and optimistic UI ownership (guide L806-820)**

- Pending state that the render reads (disabled controls, pending labels, progress, duplicate-submit prevention) belongs in setup scope and is set/cleared around the request (L808-810). Optimistic UI — rendering the expected result before the request settles — belongs in the model that owns the data, together with its recovery policy: restore the previous state or adopt the server response on failure, and let the component render the resulting error/retry (L812-820). Use optimistic only for reversible, predictable changes; wait for the response when the server chooses the final value, performs something destructive, or can reject in a way the user must resolve first (L816-819).
- App seam: no optimistic state exists in `app/` (`optimistic` and `extends TypedEventTarget` have no matches). The only client request state is pending/disabled in setup scope or entry-local flags — `pending` in `app/actions/client/public/grid-refresh-button.tsx:32`, `submitting` in `app/assets/streams/public/support-agent-stream.tsx:756-758`, `setFormEnabled(false)` in `app/assets/streams/public/agent-events-stream.tsx:313`. Adopting optimistic UI means creating the model home the guide requires; do not park optimistic state in the entry just because pending state lives there.

**`navigate()`, `link()`, and `attrs()` (guide L690-718, L431)**

- `navigate(href, options)` is for navigation that begins in code. `link(href, options)` makes a non-anchor host behave like a link: it adds `role="link"`, makes the host keyboard-focusable when needed, handles Enter and mouse/modifier-key activation, and reflects a disabled host with `aria-disabled` (L715-718). Prefer a real anchor when the markup fits. `attrs(...)` supplies default attributes without replacing explicit element props (L431-432).
- App seam: `navigate` is imported from `remix/ui` and used in `app/ui/appointment-sidebar.browser.tsx:1,79,104,127,147,160`, always with default options (no `{ history: "replace" }` anywhere in the app). **Disambiguation:** `app/actions/lists/public/lists-sidebar-keyboard.tsx:34-38` declares a local `navigate(href)` helper that assigns `handle.frame.src` and calls `handle.frame.reload()` — that is frame navigation, not the `remix/ui` `navigate()`. Grep hits for `navigate(` are not all client navigation. The `link()` and `attrs()` mixins do not appear in `app/` (the only `attrs` hits are the server's `data-rmx-preserve-attrs`; the only `link` hits are a theme color token and JSDoc). The closest hand-rolled pattern is the disabled pagination `<span aria-disabled="true">` in `app/ui/admin-report1-page.tsx:331,340`, which is not focusable and not a `link()`; adopting either mixin is new.

**Stable list keys and controlled vs uncontrolled inputs (guide L294-298, L343-395)**

- Key a list by a stable id whenever an update can reorder/insert/remove items — not by array index or a value created during render — so matching keys move existing DOM/component instances instead of pairing state with the wrong item (L294-296). An uncontrolled input keeps its value in the DOM and `defaultValue` is only its initial value; a controlled input takes `value` from state, and its `input` handler copies the DOM value into that state before `handle.update()` (L343-395).
- App seam: `defaultValue={...}` is the app's norm for filters/forms (e.g. `app/ui/lists-layout.tsx:216`), and `app/ui/dirty-form-guard.browser.tsx:29-42` explicitly treats the live `defaultValue` as the server-rendered baseline. Controlled inputs appear where a client entry owns the current value: `value={editPriority}` etc. with `on('input')` in `app/actions/lists/public/lists-client.tsx:3012,3028,3040`, and `<select value={selectedResourceId}>`/`value={year}` in `app/ui/appointment-sidebar.browser.tsx:70,95`. Index keys still exist on message lists (`key={i}` in `app/ui/customer-chat-page.tsx:104`, `key={index}` in `app/ui/support-agent-page.tsx:354`); that is fine for static markup, but do not copy it for a list that streams, reorders, or inserts (L294-296).

**Enhanced form submission (guide L742-804)**

- Intercept `submit`, call `event.preventDefault()`, and send the form's own action/method with `new FormData(form)` so the controller is unchanged. Pass the event's abort signal into `fetch(...)`; on success follow the action's redirect with `navigate(response.url, { history: "replace" })` (L752-775). Non-enhanced submissions must still receive the same redirect/error response. Choose the boundary deliberately: normal submit for a document navigation, `fetch()` when the page needs pending/inline errors before navigating, JSON when a browser-side model owns the data, polling for independent data (L796-801).
- App seam: the existing submit interception is the **agent/chat stream path**, a different synchronization boundary. `app/assets/streams/public/agent-events-stream.tsx:301-324` and `app/assets/streams/public/customer-chat-stream.tsx:815-846` `preventDefault()`, build `new FormData(form)`, and hand it to the SSE stream; `app/assets/streams/public/support-agent-stream.tsx:769-773` fetches `body: new FormData(form)` and then reloads the frame (`:797-799`); `app/ui/settings-enhance.browser.tsx:256` and `app/ui/message-compose.browser.tsx:101` use document-level `submit` capture for side effects. None follow the guide's `navigate(response.url, { history: "replace" })`. They also attach with native `form.addEventListener('submit', handler, { signal: handle.signal })` (e.g. `agent-events-stream.tsx:402`) — the app convention — rather than `on('submit', ...)`. `new FormData(form)` carries the rendered `_csrf` hidden field (`app/ui/csrf-token-input.tsx`), so interception needs no extra CSRF plumbing.

## When to Use

- You are adding a client-only mount point, custom DOM event, code-driven navigation, link-like non-anchor host, or form interception in a Remix 3 `clientEntry` and want to know which guide section owns it and whether the app already has a seam.
- You are about to copy `createRoot`, the `run()` lifecycle, `navigate`/`link`/`attrs`, `createMixin`/`handle.element`, the `on(...)` handler signal, or the guide's fetch-and-`navigate` form enhancement, and need the app's actual convention first.
- A list's DOM or component state pairs with the wrong row after an insert/reorder/sort, a controlled input fights `defaultValue`, or an enhanced submit must follow a controller redirect.
