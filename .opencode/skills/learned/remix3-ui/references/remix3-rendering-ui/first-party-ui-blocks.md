# Remix 3 First-Party UI Blocks (app styling → headless primitives)

**Source:** installed guide `node_modules/remix/guides/04-rendering-ui.md` — §"Optional headless UI primitives", with the styling sections §"Styling with css and dynamic style values" and §"Cascade layers and app-owned design tokens".

**Extracted:** 2026-09-26
**Revalidated:** 2026-11-24: toasts moved to a shell-owned `ToastHost` that renders into the overlay root (the imperative `showToast` API, vendor comparison, and CSP/style-prop deltas are unchanged; the stack is now click-through, capped at the newest three, and width-bounded). Primitive list and styling deltas last checked 2026-11-19 against source `9e4da4d3` (`@remix-run/ui` 0.14.0).

**Context:** Choosing a `remix/component/*` building block, or deciding whether to use, wrap, or replace a vendor component.

## Problem

No skill names `app/ui/theme/upstream-button.ts`, `@remix-run/ui/accordion`, or `@remix-run/ui/select`, so the primitives/ownership model is guide-only. A generic "use the vendor component" answer also misses this app's deliberate wrappers and replacement.

## Solution

Use the guide's selection model, then this app's concrete decisions.

**Selection order (installed `@remix-run/ui` 0.14.0):**

1. **Native elements styled with `css()`** — keep the real `<button>`/`<input>`/checkbox/radio and style it with `remix/component` style descriptors (guide §"Styling with css and dynamic style values"). The former `@remix-run/ui` styled `button`/`input`/`checkbox`/`radio` mixins and the `breadcrumbs` module were deleted in the 0.11 → 0.12 cleanup (#11986), so there is no vendor style mixin to import; the app vendors its own button (`app/ui/theme/upstream-button.ts`).
2. **Headless primitives** — `@remix-run/ui` 0.14.0 ships `accordion`, `anchor`, `combobox`, `form`, `listbox`, `menu`, `popover`, `select`, `tabs`, `toast`, and `toggle` (ui README "Primitives"; `animation` is the separate motion module). `toast` arrived with #12084 and the 0.13→0.14 bump changed no primitive exports. They own structural attributes, keyboard/focus behavior, and disclosure/selection state. Use `default*` for uncontrolled and the controlled prop/callback when the parent owns state (names differ by component). Use them only when the product needs their behavior or different markup, not just different colors; the app then owns labels, ARIA, and pointer/keyboard behavior. Select/combobox still need a hidden input to participate in a form. There are no `/primitives` subpaths in this build.

Interactive controls must sit inside a `clientEntry(...)` boundary, directly or via an interactive ancestor (see `remix3-client-entries`).

**Styling deltas:**

- **JSX `style` props are blocked by the app CSP.** The guide recommends the `style` prop for values that change continuously (progress, coordinates, transforms), but `contentSecurityPolicy()` sets `style-src-attr 'none'` and the component runtime writes a **string** `style` prop with `setAttribute('style', …)` (`@remix-run/component/src/runtime/vdom.ts:2239-2242` at source `8a8adc7b`; style *objects* go through CSSOM `patchStyleObject` at `:2332`, which CSP does not block), so a string `style` prop never reaches the page. Use `css()` for bounded value sets (generated classes are content-addressed and cached by serialized style, so a repeated value reuses its class) and CSSOM (`el.style.x = …` in a ref/handler) for continuously changing geometry. Examples: `app/ui/scaffold-home-page.tsx` (bounded progress widths/tones), `app/actions/admin/uploads/controller.tsx` (quota bar), `app/ui/appointment-grid.browser.tsx` (drag transforms). Policy detail: `remix3-server` § Security → `security-gotchas/security-checks.md`.
- **Single-site named styles are a pre-#12193 convention.** The guide's placement rule (keep a descriptor used at one JSX site inline; name it when multiple sites share it or a variant map clarifies; extract at the second use) postdates most of this app: 472 of 1,068 `css()` descriptors were named constants used at exactly one site at the 2026-11-14 audit, and the population has grown to ~1,390 raw `css({` sites since. Follow the guide for new code; do not churn the existing set without a dedicated sweep. The variant half of the rule is live: `app/actions/lists/public/lists-view.tsx` puts the grabbed-row highlight behind `&[data-grabbed]` in the row style instead of a second `css()` call.

**App-specific deltas:**

- **Button is wrapped, not used raw.** `app/ui/theme/button.ts` imports `app/ui/theme/upstream-button.ts`, adds `secondary`/`danger`/`dangerOutline` tones, and rebinds the mixin host type to `HTMLButtonElement` (a type-level workaround for TypeScript's order-sensitive recursive assignability). `buttonLink()` rebinds to `HTMLAnchorElement` so a navigation link is styled as a button without nesting a `<button>` inside an `<a>`.
- **The vendored button must keep upstream's *attribute* mixin, not just its CSS.** The #11948 split copied only the three CSS descriptors into `app/ui/theme/upstream-button.ts` and dropped `buttonDefaultAttrs`, which defaults a native `<button>` host with no explicit `type` to `type="button"`. Without it, every untyped `<button mix={[button()]}>` — including click-only actions — renders as an implicit `type="submit"`. `tsc` and render-tree tests cannot see this; assert the rendered `type` in a browser test (`app/ui/theme/button.test.browser.tsx`). Restore it by re-adding a `createMixin` that returns `createElement(handle.element, { ...props, type: 'button' })` when `hostType === 'button'` and `props.type === undefined`.
- **Never nest a `<button>` in an `<a>` — it only *looks* fine outside a form.** In Chromium and Firefox alike, `<a><button>` navigates when there is no form owner, but inside a `<form>` the inner button's default submit wins and the link silently submits the form. That is how the `/verwaltung/appointments` Zeitraum/Status chips broke (they reloaded `?filter=`, dropping `period`/`status`) once the vendoring removed the implicit `type="button"`. Style the `<a>` with `buttonLink()` and enforce the content model with the repo-local oxlint rule `remix-a11y/no-nested-interactive` (`scripts/oxlint-plugins/no-nested-interactive-plugin.ts`, registered in `.oxlintrc.json`).
- **Vendor Inter is overridden with `inherit`.** Upstream's button CSS and the copied menu style values hardcode `Inter`; the app sets both to `inherit` so controls follow the surrounding surface — JetBrains Mono on app pages, Inter on the Inter-based landing page (`app/ui/scaffold-home-page.tsx`). Keep new control styles on `inherit` (or the theme token), not an upstream font literal.
- **Breadcrumbs are app-owned.** `app/ui/breadcrumbs.tsx` renders the trail directly: the vendor breadcrumbs component was deleted in the 0.11 → 0.12 cleanup (#11986), so there is no vendor component to wrap. It uses theme tokens — see `remix3-theme-conformance` and `remix3-css-and-layout` — and the document shell maps an explicit `data-theme` to `color-scheme`, so any remaining vendor `light-dark(...)` palettes follow the app theme.
- **Menus use primitives, styled by an app wrapper.** Context menus import `MenuList`/`MenuItem` from `app/ui/theme/menu/index.tsx` and `onMenuSelect` from `@remix-run/ui/menu`, inside browser clientEntries.
- **Toasts stay app-owned; `@remix-run/ui/toast` is not adopted.** Since #12084 the build ships a toast primitive (`@remix-run/ui/toast`; the installed `dist/toast.d.ts` is the API). It is a *component system*: `createToastManager()` returns a browser-only manager (`add`/`close`/`closeAll`; `items` newest-first with id/revision; `timeout` starts when presented; `announcement` overrides the spoken title/description), `Context` renders the manager's items and must be **mounted in a component tree**, `root` provides a labelled keyboard-reachable region, `ItemContext`+`item` add dialog semantics/focus recovery/an optional countdown, `title`/`description`/`close` bind consumer-authored markup, and the consumer owns positioning and styling. This app keeps its own renderer but now has the document-level host the earlier note said was missing: `app/ui/toast.ts` is only the imperative `showToast(message, tone)` API, which dispatches `app:toast-request` on `document`; `app/ui/toast-host.browser.tsx` is the single shell `clientEntry` (mounted by `app/ui/document.tsx`) that owns the viewport, call-order stack, error/success theme tones, live-region roles (`alert`/`status`), and the 3.5 s display + 300 ms exit timers, and renders through `OverlayPortal` into `#app-overlay-root` (outside the page scroller and every frame, so toasts survive frame swaps). The stack is non-interactive: the viewport and every toast stay `pointer-events: none` so toasts never block the chrome underneath (no close button, pause-on-hover, or countdown), each toast is bounded to `min(28rem, calc(100vw - 2rem))` with `box-sizing: border-box` and `overflow-wrap: anywhere`, and a burst keeps only the newest three messages (`MAX_TOASTS = 3`), dropping older toasts immediately and clearing their timers/entrance `requestAnimationFrame`. Its callers are the appointment grid and its helpers (`app/ui/appointment-grid.browser.tsx`, `app/ui/appointment-grid-lib.ts`) and the types panel (`app/ui/appointtype-panel.browser.tsx`), which are independent islands that can be mounted on the same page; the shell host is what keeps one stack across them. There is no close button, title/description split, pause-on-hover, or countdown. Adopting the vendor manager is now a host-internal swap rather than a placement change, but it would still add UX the app does not have; revisit only if the product wants that, and keep the German strings. `app/ui/toast.test.browser.tsx` pins the host contract (overlay-root destination, one viewport, call-order stacking, newest-three cap, long-message width, click-through pointer-events, tone/role split, timeout removal), `app/ui/toast-host.test.e2e.ts` proves the shell host is mounted and receives the bridge event, and `app/ui/toast-frame-survival.test.e2e.ts` proves a toast survives an appointment-content week swap without a document reload.

## When to Use

- Adding a styled button/input or an `@remix-run/ui` primitive (select/accordion/menu/tabs) to a page and choosing between app-owned styling and a primitive.
- Deciding whether to use a vendor `remix/component` component, wrap it (as with button), or replace it (as with breadcrumbs).
- A link styled as a button silently submits/reloads the surrounding form, or an untyped `button()` control starts submitting a form after a vendor bump.
- Moving from an app-owned control to a primitive when custom markup or behavior is needed.
- Adding a transient error/success message (toast): the app's `showToast` → shell `ToastHost` pipeline versus the vendor `@remix-run/ui/toast` component system, and what a migration would require.
