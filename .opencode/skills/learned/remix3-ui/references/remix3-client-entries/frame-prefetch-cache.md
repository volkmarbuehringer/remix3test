# Frame prefetching with a one-shot response cache

**Extracted:** 2026-10-23 · **Updated:** 2026-11-12 · **Pin:** remix 3.2.0 (preview release `v0.20261112.171030-main-17a9e392` / source `17a9e392`)
**Vendor:** `@remix-run/component/src/runtime/prefetch.ts` (`startPrefetching`, `startViewportPrefetching`, `getIntentAnchor`), `run.ts` (`prefetch` option), installed guide `node_modules/remix/guides/05-interactivity.md` §"Prefetch links before navigation".

## Why the default prefetcher is not enough here

- `app/assets/entry.tsx` replaces the runtime default with `run({ resolveFrame })`: every frame request adds `X-Remix-Frame`/`X-Remix-Target`, a one-shot `X-Agent-Prefill` payload, `cache: 'no-store'`, and the 4xx-renders / 5xx-`ErrorCard` / 401-redirect policy, then reconciles `X-Remix-Redirect-To` into `frame.src`.
- The default prefetcher (`createDefaultPrefetch`) fetches HTML on its own and discovers JavaScript/CSS/image/font `<link rel="prefetch">` hints. It never goes through the custom resolver, and the navigation resolves again — so its HTML is discarded and the app pays a second SSR per hovered link.
- Replacing it also drops the asset-hint half. `app/assets/frame-asset-prefetch.browser.ts` restores it: after a successful warm, a clone of the HTML is parsed inertly and destination assets get low-priority hints.
- The 3.1 answer is the `prefetch` hook: the runtime calls it on intent, the app stores the response the navigation *would* have fetched, and `resolveFrame` claims it. `run.ts` documents exactly this pairing ("use it with `resolveFrame` to reuse uncacheable HTML").

## Wiring

- `app/assets/frame-prefetch.browser.ts` — the one-shot cache: `prefetchFrame(src, options)` (the `PrefetchFrame` hook; the warm promise is kept in an `inFlight` map), `claimPrefetchedFrame(url, target, signal)` (stored entry **or** awaits a warm still in flight), `takePrefetchedFrame(url, target)` (sync claim), `clearPrefetchedFrames()`. Key is `target + ' ' + absolute href`; entries are single use, TTL 10 s, max 8, and consuming one clears the rest.
- `app/assets/frame-asset-prefetch.browser.ts` — `prefetchFrameAssets(response, sourceUrl)` parses the warmed HTML and emits `<link rel="prefetch">` hints; `clearPrefetchedAssets()` is the test-only pending-hint cleanup.
- `app/assets/frame-response.browser.tsx` — one request path, two modes: `fetchFrameResponse` classifies the outcome, `resolveFrameResponse` is navigation mode, `prefetchFrameResponse` is prefetch mode.
- `app/assets/entry.tsx` — `run({ prefetch })`; `resolveFrame` **awaits** `claimPrefetchedFrame` for a plain GET (method `get`/undefined, no `formData`), deletes the prefill entry on a hit, reconciles the redirect header for both cached and fetched responses, and only clears + fetches when the claim misses.

## Invariants

- **A prefetch must never navigate the document.** Redirect-with-`target` and 401 resolve to `undefined` in prefetch mode; only navigation mode calls `window.location.assign`. Otherwise hovering a stale link would yank the page.
- **Never consume `agentPrefillMap` during a prefetch.** The warmed HTML already contains the prefilled content; deleting the one-shot entry would starve a later navigation that misses the cache. The hit path deletes it; the real fetch keeps deleting on `response.ok`.
- **A click that beats the warm must await it, not refetch.** The runtime starts the prefetch on `pointerdown`, tens of ms before the click navigation. `claimPrefetchedFrame` awaits the in-flight promise (honoring the navigation `signal`) so a fast click does not clear the warm and start a second SSR; `clearPrefetchedFrames()` only runs after the claim misses. Do not reorder this into a sync `take` + clear.
- **Only plain GETs are warmable.** Cache lookups are gated on `isPlainGet`; `frame.reload({ method, body })` POSTs and form-data GETs bypass the cache entirely (the key does not encode method or body).
- **Safari traversal scroll with warmed frames.** Since #12274, when a traversal renders from content that is already available (including a response claimed from this cache), WebKit restores the destination scroll after the frames render instead of keeping the page-being-left's position. Warmed back/forward navigation therefore no longer lands at the wrong offset. The app's `scroll-restoration` e2e guards the window-scroll case; nested `[data-page-scroller]`/`[data-grid-scroll]` reset remains app-owned (`app/ui/page-scroll-reset.browser.tsx`).
- **5xx is never cached.** The recovery card is a client-side component, not a reusable fragment; 4xx validation fragments are cached because a real navigation renders them.
- **CSP nonces.** Frame fragments carry the nonce of the response that rendered them. Reuse is same-document and short-lived; the app's frame content has inert JSON scripts plus import maps that the runtime appends with the installed map's nonce. Do not introduce executable `nonce={getCspNonce()}` inline scripts into frame fragments — a warmed copy would carry a stale nonce.
- **Warm requests are `priority: 'low'`**, matching the vendor default, so a hover warm does not compete with the navigation it accelerates; navigation requests keep the browser default.
- **`rel=prefetch` is feature-gated per engine.** WebKit (Playwright 27.2) reports `link.relList.supports('prefetch') === false`, while Chromium and Firefox report `true`. `prefetchAsset()` skips hint creation on WebKit, so a warm still serves the frame HTML but destination assets start cold; do not remove the guard. The opt-in WebKit browser suite asserts the no-op path.
- **Asset hints are part of the warm.** `prefetchFrame()` calls `prefetchFrameAssets()` after storing the response. Discovery mirrors the vendor default: clone + inert `<template>` parse, honor `<base href>`, recurse into nested `<template>` content, skip assets the document already has, dedupe by `href`/`as`/`crossorigin`/`integrity`/`referrerpolicy`, and remove each hint on `load`/`error`. Hints are independent of the one-shot HTML cache: `clearPrefetchedFrames()` does not remove them, because a destination entry module or stylesheet stays useful after the one-shot fragment is invalidated. Do not run scripts from the parsed HTML or inject its nonce-bearing nodes.
- **Targeted warms resolve against the most recent `run()`.** Since #12245 the named-frame registry is per runtime; the module-level `prefetch(href, { target })` lookup (`prefetch.ts` → `getNamedFrame`) reads the frames published by the most recently started `run()`. The app starts one runtime in `app/assets/entry.tsx`, so the target lookup is unaffected; a second `run()` in the same document would redirect targeted warms to its own frames.
- **Head reconciliation is not vendor-identical.** The vendor registers its hints in the internal `pendingPrefetchLinks` WeakSet, which `frame.ts`'s head diff preserves. These app-owned hints are outside that set, so a top-level frame navigation can remove an in-flight hint without firing `load`/`error`. `prefetchAsset()` treats a disconnected pending hint as stale and re-creates it, and a 15 s fallback timer clears a hint that never settles; without both, the pending promise would suppress that asset for the rest of the document's lifetime.
- **Viewport prefetch uses the same override.** `startPrefetching(signal, prefetch)` installs the app's hook and still starts `startViewportPrefetching()`; the observer calls the active `prefetchFrame`, so `data-rmx-prefetch="viewport"` warms through the app's one-shot cache. Since #12256 a link that enters view during a scroll — including in a nested scroller, because the listener is capturing on `document` — waits 150 ms after the last scroll and is prefetched only if still visible; links already in view without a scroll prefetch immediately. Since #12286 pending viewport warms pause while `document.hidden` and recheck intersections/eligibility on `visibilitychange`, and disposal clears the timer/queue. The default prefetcher's idle-deferred HTML asset discovery does not apply here because the app discovers assets itself.

## Adoption points

Intent anchors: admin-lists filter tabs (Alle/Mit Elementen/Leer) and numbered page links, admin-users filter tabs, and the appointment-sidebar week arrows. Every admin/client grid pager's prev/next uses `data-rmx-prefetch="viewport"` — lists, users, appointments, messages, offerings, offering configs, resources, uploads, webhook requests, chatlog, and the clients grid. These links enter view only at the grid footer, so the runtime's scroll settle avoids warming links passed on the way; the numbered page links stay intent-only so a visible pager does not warm every page in its window. The runtime reads intent anchors **on the anchor itself** (`getIntentAnchor` → `a[href][data-rmx-prefetch="intent"]`) and viewport anchors through the observer's `getRequest` (`data-rmx-prefetch === 'viewport'`), so add the attribute per link. Prefer same-origin GET anchors that already carry `data-rmx-target`; skip `data-rmx-document` links (runtime filters them), downloads, and JS-triggered reloads (a reload with no anchor never prefetches). Do not mark grid rows or filter tabs viewport: they are visible on load, so each would start a full SSR warm immediately.

## Tests

- `app/assets/frame-prefetch.test.browser.ts` — single use, concurrent dedupe, in-flight claim (one request), abort-while-waiting, target keying, cross-origin skip, sibling invalidation, refused responses.
- `app/assets/frame-asset-prefetch.test.browser.ts` — scripts/styles/modulepreloads/image/font preloads, `<base>` resolution, nested templates, document dedupe, `imagesrcset`/media skips, non-HTML/partial responses, re-creation after a disconnected hint, and the `prefetchFrame()` wiring. Uses a `MutationObserver` plus a bounded `waitFor` poll because hints disappear on the first 404; do not assert on the live DOM after a fixed sleep.
- `app/actions/admin/admin-lists-prefetch.test.e2e.ts` — the real runtime. Intent: hover the marked "Leer" tab, assert one fragment request, click, assert the count stays 1 and the URL moves to `status=empty`. Viewport: seed 11 lists under a unique filter, open the filtered grid, scroll the pager's "Nächste Seite" link into view, assert one fragment request, click, assert the URL moves to `offset=10` and the count stays 1. Both pass on Chromium and Firefox.
- `app/actions/client/clients-prefetch.test.e2e.ts` — the separate `app/actions/client/grid-page.tsx` pager against the seeded 200 clients: scroll "Weiter" into view, assert one fragment request, click, assert `offset=15` and the count stays 1. Passes on Chromium and Firefox.
- Attach the request listener and `waitForRequest` **before** `goto` in both e2e tests: a pager already in view prefetches on load, so attaching after the grid appears misses the warm. Match on path + `offset` + `x-remix-frame: true`, then assert the count is still 1 after the click.
- `app/assets/frame-asset-prefetch.test.browser.ts` § WebKit — when `relList.supports('prefetch')` is false, the suite awaits `prefetchFrameAssets()` and asserts zero hint elements; the hint-shape assertions remain on Chromium/Firefox.
- `app/assets/frame-response.test.browser.ts` § `prefetchFrameResponse` — no navigation on redirect/401, 5xx skipped, 4xx cached, prefill retained on prefetch and consumed on navigation.
