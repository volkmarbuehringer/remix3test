## Problem

The guide covers the runtime and mixin APIs completely, but this app has its own client wiring (`app/assets/entry.tsx`, `app/assets/error-card.browser.tsx`) and its own shared handler conventions that diverge from the guide's examples in ways that are easy to misread: `createRoot` is used for a fatal-error takeover rather than a widget; `navigate` is used only by the scroll-restoration entry, while frame navigation uses `handle.frame.reload`; the existing form interception is the SSE/JSON stream path, not the guide's fetch-and-redirect enhancement; the app uses the `on(...)` second-arg signal only in `app/ui/pending-submit.browser.tsx` (for `rmx:navigation`, renamed from `rmx:submission` at #12306); and no app code uses `link()` or `attrs()`. Treating any of these as "already implemented like the guide" leads to wrong edits.

## Solution

**Client-only root — `createRoot(container)` (guide §"Mount client-only UI with createRoot")**

- The root owns its container. `root.render(node)` schedules a tree, `root.flush()` applies pending work synchronously, and `root.dispose()` removes the tree and runs cleanup; the guide's widget example disposes on `pagehide` with `{ once: true }` (§"Mount client-only UI with createRoot"). Reserve `createRoot` for UI with no server-rendered component to hydrate; normal page UI starts on the server via `clientEntry(...)` so users are not left waiting on JavaScript (§"Mount client-only UI with createRoot").
- App seam: the only `createRoot` in the app is the fatal-error takeover — `renderFatalError()` in `app/assets/error-card.browser.tsx:115-138` calls `createRoot(document.body).render(<ErrorCard .../>)`. It runs from `run()`'s error listener (`app/assets/entry.tsx:60-72`) **after** `app.dispose()` and after `fadeOutBody()` clears `document.body`, so the root replaces the whole document. It never registers the guide's `pagehide` dispose (the runtime it could outlive is already gone) and never calls `root.flush()`/`root.dispose()` itself. A future non-fatal client-only root (a widget in a page shell) is new behavior: copy the guide's `pagehide` dispose, not the error card's terminal pattern.

**Browser runtime lifecycle — `run()` (guide §"Booting the browser runtime with run")**

- `app.ready()` resolves after the initial client entries hydrate. `app.flush()` synchronously applies pending component updates — the supported way to observe the DOM immediately, scoped by the guide to tests and integrations. `app.dispose()` removes the runtime's components and listeners (§"Booting the browser runtime with run").
- App seam: `app/assets/entry.tsx:18-19` keeps the `run()` result in module `app`, but the entry never calls `app.ready()` or `app.flush()`. The single lifecycle call is `app.dispose()` in the error listener at `:60-61`, immediately before the error card mounts. Tests that need to wait for hydration create their own `run()` result (`app/ui/frame-reload-behavior.test.browser.tsx`), so they are not a production seam. The app relies on `app.addEventListener('error', ...)` (`:60`) for failure handling, and `remix3-testing` owns how tests drive client DOM without `app.flush()`.

**Custom event mixin — `createMixin` + `handle.element` (guide §"When to create a custom event mixin")**

- Build the interaction from low-level events in setup scope, then dispatch one semantic typed event (`LongPressEvent extends Event` with `{ bubbles: true }`) that consumers attach with `on(...)`. `handle.addEventListener("insert"|"remove", ...)` is the **mixin handle's** own lifecycle events (not a DOM `addEventListener`): `insert` supplies `event.node`, `remove` is the cancel hook. The mixin returns `<handle.element mix={[...]} />`. Augment `HTMLElementEventMap` in a `declare global` block so the consumer's `on(longPressType, ...)` is typed, and namespace the name (`app:longpress`) to avoid collisions (§"When to create a custom event mixin").
- App seam: `app/actions/lists/public/lists-drag-mixin.ts` uses `createMixin<HTMLElement, [ListsDragContext]>(..., { ssr: false })` and returns `handle.element` for its delegated drag behavior; `app/ui/theme/upstream-button.ts` uses the same API for its host-type attribute default. No custom DOM *mixin* events are dispatched outside tests, which dispatch native `submit`/`input` (e.g. `app/assets/streams/streams.test.browser.tsx:91`); follow those two sites and the guide rather than inventing a new mixin event layer (`remix3-ui § Client Entries` → `references/remix3-client-entries/browser-only-behavior-mixin.md`). App-level imperative bridges are a separate mechanism: document `CustomEvent`s (`app:confirm-request` in `app/ui/confirm-delete.browser.tsx`, `app:toast-request` in `app/ui/toast.ts`) consumed by a shell host; see `references/remix3-client-entries/shell-overlay-portal.md`.

**Listener lifetime — `handle.signal` and the `ref` signal (guide §"Events with on", §"DOM references, global events, and cleanup")**

- Listeners on `window`, `document`, or a media query belong to the component, not to the page: register them after the client commit (`handle.queueTask` in setup scope) with `{ signal: handle.signal }`; a hidden host marker may instead register its document listeners in `ref` and set a `data-*-ready` attribute after attaching (`app/ui/toast-host.browser.tsx`), so the ref signal owns their lifetime. Element-owned listeners go through `ref((node, signal) => …)` and use the ref's `signal`, which aborts when that node is removed. A module-scoped "registered once" flag is not a substitute: it keeps a listener alive after the entry that owns it is disposed, and any closure over `handle` then points at a dead runtime. The ref signal is also the right home for a pending timer/listener batch owned by that node.
- App seam (revalidated 2026-11-14, guard updated 2026-11-24): `app/ui/report1-filter-autosubmit.browser.tsx` is the reference pattern (setup `handle.queueTask`, document listener with `handle.signal`). Fixed in this audit: `app/ui/appointments-new-resource-search.browser.tsx`, `app/ui/appointments-new-step2.browser.tsx`, `app/ui/message-expand.browser.tsx`, and `app/ui/admin-chatlog-detail.browser.tsx` no longer use module-scoped once-guards; their document listeners are installed after commit with `handle.signal`, and the chatlog pane's `MutationObserver` is per entry and disconnected from `handle.signal`. `app/ui/dirty-form-guard.browser.tsx` is the deferred-navigation guard (per-form `AbortController`, frame-swap re-bind, one-shot replay/unload flags); see `references/remix3-client-entries/dirty-navigation-guard.md`. `app/actions/lists/public/lists-search.tsx` / `lists-sidebar-keyboard.tsx` abort their element listeners and pending debounce from the ref signal. Regression tests: the disconnect cases in `appointments-new-resource-search.test.browser.tsx`, `appointments-new-step2.test.browser.tsx`, `message-expand.test.browser.tsx`, `admin-chatlog-detail.test.browser.tsx`, `dirty-form-guard.test.browser.tsx`, `lists-search.test.browser.tsx`, and `lists-sidebar-keyboard.test.browser.tsx`; the deferred-navigation replay is covered end-to-end in `app/actions/admin/lists/lists-ux.test.e2e.ts`.
- The guide's `KeyedList` interval cleanup (#12193) is the same rule for component-lifetime timers: add the `handle.signal` abort listener directly after starting the timer. `app/assets/streams/public/support-agent-stream.tsx:220-247` (retry countdown) already does this.
- App seam (second pass): `app/actions/lists/public/lists-row-actions.tsx` used to abort its document listener batch only at the start of the next `init()`, so a disposed entry kept handling `pointerdown`/`keydown`/`click` for rows it no longer owned. Its `ref((element, signal) => …)` now registers `abortListeners` on the ref signal (`init()` still calls it before re-binding). Regression: `lists-row-actions.test.browser.tsx` §"stops handling document events after the entry is disposed" (dispatch outside pointerdown + Escape after cleanup, assert the menu stays open).

**Cancellation granularity (guide §"State, updates, and post-render tasks", §"Async work and cancellation")**

- `handle.update()` schedules work and its promise resolves to an `AbortSignal`, but the runtime **cannot** abort it between `await handle.update()` and the next synchronous statement — `input.focus()` needs no check. Capture the signal only when more async work follows: pass it to `fetch(href, { signal })` and re-check `signal.aborted` after each later `await` before touching state (§"State, updates, and post-render tasks"). The second argument of an `on(type, (event, signal))` handler (§"Async work and cancellation") is the signal for work where the latest event should replace earlier work; it aborts on re-run **or** element removal. The `queueTask` and `handle.signal` aborts are already covered by `references/queuetask-over-raf.md` and `remix3-frame-cliententry` and are not restated here.
- App seam: `app/ui/pending-submit.browser.tsx` uses the `on('rmx:navigation', async (event, signal) => …)` second-arg signal to tie its pending state to its own submission (#12306; the event was `rmx:submission` at #12183); everything else cancels async work with `handle.signal` on native listeners (e.g. `app/assets/streams/public/agent-events-stream.tsx:229,236-243`), a local `AbortController` (`app/actions/lists/public/list-name-edit.tsx:47-49`), or the signal returned by `handle.frame.reload()` (`app/actions/client/public/grid-refresh-button.tsx:45-50`). When you attach with native `addEventListener` — because the target is outside the render tree or you are inside a `queueTask` — you do not get the per-handler signal; pass your own controller or `handle.signal`, as those sites do.
- App seam (second pass): the appointment grid binds `pointermove`/`pointerup`/`pointercancel` on `window` for the duration of a drag/resize (`app/ui/appointment-grid.browser.tsx` `bindWindowEvents`). They now live on one `AbortController` per gesture, aborted by `unbindWindowEvents` and by `handle.signal`; disposal also clears the gesture state and releases the shared `interactionState.active` flag (otherwise an SSE invalidate reload that disposed the entry mid-drag suppressed every later reload). The `endDrag`/`endResize` continuations re-check `handle.signal.aborted` after `await Promise.allSettled(saves)` before updating state or reloading. Regression: `appointment-grid-gestures.test.browser.tsx` §"unbinds window gesture listeners when the entry is disposed mid-drag".
- App seam (second pass): `createAgentEventsStreamController` now takes the entry's lifetime `signal` (`AgentEventsControllerOptions.signal`, passed from `agent-events-stream.tsx`) and aborts the in-flight SSE stream on disposal, matching `support-agent-controller`/`customer-chat-controller`. Regression: `agent-events-controller.test.ts` §"cancels an in-flight stream when the entry lifetime signal aborts".

**Committed-DOM barrier for async browser APIs (guide §"State, updates, and post-render tasks")**

- `handle.update()`'s promise resolves **after the DOM commit**, not when the render is scheduled. `update()` queues a resolver in the component task list; `renderComponent` drains it through `scheduler.enqueueTasks(tasks)` *after* `diffVNodes`, and the scheduler flushes that queue in the post-commit phase (`@remix-run/component` source `53dad21e`: `runtime/vdom.ts:101-133` (the `update()` resolver in `createComponent`), `runtime/vdom.ts:1601-1629` (`renderComponent`, with `scheduler.enqueueTasks(tasks)` at `:1628`), `runtime/vdom.ts` `flush()` at `:596`, `createScheduler` at `:529`; #12314 folded the former `scheduler.ts` into `vdom.ts`, and #12429/#12435 folded `reconcile.ts` and `component.ts`'s runtime helpers into `vdom.ts`). `await handle.update()` is therefore a supported "the DOM now reflects this state" barrier — call it from an event handler or the update callback, never during setup/render.
- Use it when an async browser API takes a callback and snapshots the DOM after that callback settles, where `queueTask` cannot help because fire-and-forget tasks have no awaitable completion: `document.startViewTransition(async () => { items = next; await handle.update() })`. The transition captures the **new** state only after the promise resolves; `startViewTransition(() => { items = next; void handle.update() })` returns before the render flushes and the new snapshot misses the change.
- Testing corollary: a View Transition's snapshot overlay suspends hover hit-testing until it clears, so a `:hover`-driven visibility assertion can read empty mid-transition even though the settled state is correct. Wait for the observable settled state (or `transition.finished`), never a fixed timeout. The `/lists` row-toolbar e2e hit exactly this after the reorder gained a transition.
- App seam: `app/actions/lists/public/lists-view-transition.ts` — row names applied before the old snapshot, re-applied after the update resolves for re-created nodes, cleared on `finished`, with feature/reduced-motion/instant fallbacks. Frame swaps have no equivalent pre-commit hook; see `remix3-frame-cliententry/references/frame-navigation.md` § Same-Document View Transitions Around Frame Reloads.

**Pending and optimistic UI ownership (guide §"Pending and optimistic UI")**

- Pending state that the render reads (disabled controls, pending labels, progress, duplicate-submit prevention) belongs in setup scope and is set/cleared around the request (§"Pending and optimistic UI"). Optimistic UI — rendering the expected result before the request settles — belongs in the model that owns the data, together with its recovery policy: restore the previous state or adopt the server response on failure, and let the component render the resulting error/retry (§"Pending and optimistic UI"). Use optimistic only for reversible, predictable changes; wait for the response when the server chooses the final value, performs something destructive, or can reject in a way the user must resolve first (§"Pending and optimistic UI").
- App seam: no optimistic state exists in `app/` (`optimistic` and `extends TypedEventTarget` have no matches). The frame-navigation pending seam is `app/ui/pending-submit.browser.tsx:48-60`: it listens to `rmx:navigation` on the button (the submitter, so the event targets it), awaits `event.finished`, keeps the button **enabled** (guide 09), and uses the handler signal so a superseded submission cannot clear a newer submission's pending state. `app/ui/filter-autosubmit.browser.tsx:127-145` observes `rmx:navigation` on `document` only to remember the submitted filter value, skipping navigations whose `element` is not the owning form (the event also fires for links and Back/Forward; the form node is replaced by the reload), and uses `reloadStart` solely for programmatic reloads that have no initiating element. Other client request state is pending/disabled in setup scope or entry-local flags — `pending` in `app/actions/client/public/grid-refresh-button.tsx:32`, `setFormEnabled(false)` in `app/assets/streams/public/support-agent-stream.tsx:495` (controller calls at `:337,:357,:419`) and in `app/assets/streams/public/agent-events-controller.ts:147,:264`. Adopting optimistic UI means creating the model home the guide requires; do not park optimistic state in the entry just because pending state lives there.

**`navigate()`, `link()`, and `attrs()` (guide §"Client navigation", §"Composing behavior with mix")**

- `navigate(href, options)` is for navigation that begins in code. `link(href, options)` makes a non-anchor host behave like a link: it adds `role="link"`, makes the host keyboard-focusable when needed, handles Enter and mouse/modifier-key activation, and reflects a disabled host with `aria-disabled` (§"Client navigation"). Prefer a real anchor when the markup fits. `attrs(...)` supplies default attributes without replacing explicit element props (§"Composing behavior with mix").
- App seam: `app/actions/scroll-restoration/public/scroll-restoration.tsx:82` is the app's only `navigate()` call (it drives `push`/`replace` after a scroll restore). Frame navigation elsewhere uses `handle.frame.reload({ src })` — `app/actions/lists/public/lists-sidebar-keyboard.tsx:63` and the local `navigateFrame` helper in `app/actions/lists/public/lists-client.tsx:450-452` — which is not the `remix/component` `navigate()`. `app/ui/appointment-sidebar.tsx` is server-rendered and imports no `navigate`. The `link()` and `attrs()` mixins do not appear in `app/` (the only `attrs` hits are the server's `data-rmx-preserve-attrs`; the only `link` hits are a theme color token and JSDoc). The closest hand-rolled pattern is the disabled pagination `<span aria-disabled="true">` in `app/ui/admin-report1-page.tsx:337-338,344-345`, which is not focusable and not a `link()`; adopting either mixin is new.
- `updateUrl(href, options)` (component #12110) reflects state the page already renders without fetching, rendering, or changing scroll/focus. Unlike a raw `history.replaceState`, it preserves history state and syncs Remix's top-frame source. App seam (2026-11-05): `app/assets/streams/public/support-agent-controller.ts` `reflectThreadInUrl()` and `app/assets/streams/public/customer-chat-controller.ts` `clearFreshParam()` pass their component lifetime signal and use it for URL-only state changes; a raw replace there cleared history state and left the top frame pointed at the pre-update URL. Second pass (2026-11-17): the SSE `navigate` handlers in `support-agent-controller.ts` and `agent-events-controller.ts` no longer call `window.history.replaceState`/`pushState`; both use `updateUrl(href, { history: 'push' (when requested), signal })`, which waits for the frame navigation it accompanies and keeps the top-frame source in step with the address bar.

**Stable list keys and controlled vs uncontrolled inputs (guide §"State, updates, and post-render tasks", §"Controlled and uncontrolled inputs")**

- Key a list by a stable id whenever an update can reorder/insert/remove items — not by array index or a value created during render — so matching keys move existing DOM/component instances instead of pairing state with the wrong item (§"State, updates, and post-render tasks"). An uncontrolled input keeps its value in the DOM and `defaultValue` is only its initial value; a controlled input takes `value` from state, and its `input` handler copies the DOM value into that state before `handle.update()` (§"Controlled and uncontrolled inputs").
- **Failure mode the guide does not state:** a controlled `value={...}` input whose handler updates state but **omits `handle.update()`** does not just go stale — `@remix-run/component` attaches a controlled-reflection `input`/`change` listener (`createControlledState` in `vdom.ts:986-1049`; closure-backed since #12429) that *restores the DOM value toward the last-rendered value* on every event. So the field snaps back mid-typing: the user can't compose text and a picked value "vanishes" until some unrelated render syncs it. The symptom reads as **"adding tags/date is very slow / never shows up"** — check for a missing `handle.update()` (or an accidental controlled `value=`) before suspecting render cost. **`<select>` (and a controlled checkbox/radio) is exempt from the `input`-path restore** (`handleEvent` returns early for `input` when `checked` is controlled or the node is a select, `vdom.ts:997`), but since #12204 select-level `value`/`defaultValue` are supported: use `defaultValue` for a mount-only initial choice and `value` + `handle.update()` for a controlled select. Its `change` handler must still re-render; on a *reused* node assert `el.value` in a `ref` callback (diffProps skips when `prev === next` and only sets the `value` *property* on change) because `defaultValue` is initialization-only.
- App seam: `defaultValue={...}` is the app's norm for filters/forms (e.g. `app/ui/lists-layout.tsx:310`), and `app/ui/dirty-form-guard.browser.tsx:29-42` explicitly treats the live `defaultValue` as the server-rendered baseline. The lists inline row editor is the cautionary example of the failure mode: it rendered date/tags as controlled `value={editDue}`/`value={editTags}` with `setEditDue`/`setEditTags` setters that never re-rendered, so typed input was reverted. It is now **uncontrolled** — `defaultValue={editDue}` / `defaultValue={editTags}` plus `defaultValue={editPriority}` for the per-item priority select (the editor remounts per row, so no post-mount `ref` is needed), mirroring the label field. The year/resource `<select>` controls in `app/ui/appointment-sidebar.tsx:68,78` are now server-rendered (`selected={res.id === selectedResourceId}` at `:70`, `selected={y === year}` at `:80`), not controlled client inputs (app re-checked 2026-10-14). Guard: `app/actions/lists/public/lists-meta-inputs.test.browser.tsx` — types tags and sets a date with no re-render, asserts the DOM keeps them and the commit payload is verbatim. Index keys still exist on message lists (`key={i}` in `app/ui/customer-chat-page.tsx:143`, `key={index}` in `app/ui/support-agent-page.tsx:393`); that is fine for static markup, but do not copy it for a list that streams, reorders, or inserts (§"State, updates, and post-render tasks"). The appointment grid's day headers key on `day.date` (`app/ui/appointment-grid.browser.tsx:297`) because week navigation changes the dates, so an index would pair a header node with a different day.

**Client-entry props refresh across frame reloads (guide §"Client navigation")**

- A frame reload reconciles the response into the live DOM, so client entries inside the frame keep their setup state **and receive the new serialized props**. A 2026-11-17 probe (`renderToStream` + `run` + `frame.reload()`, Chromium and Firefox) showed the client instance was reused while the render function received the reloaded prop value, and a click-incremented setup counter survived. Consequence: read changing values from `handle.props` **during render or at event time**; a `let props = handle.props` snapshot in setup freezes values the frame has already replaced. When an entry's identity depends on a prop (an editor bound to an edit target), reset the derived draft state when that prop changes, or the preserved state pairs with the wrong entity.
- App seam: `app/actions/admin/webhook-requests/public/webhook-composer.tsx` snapshotted `handle.props` in setup and initialized `rows` once, so a frame reload that retargeted the same-position composer from row A to row B kept showing and submitting A's payload. It now reads `handle.props` in render and rebuilds `rows` when `editId` changes (a same-target reload keeps the in-progress draft). Regression: `app/actions/admin/webhook-requests/public/webhook-composer.test.browser.tsx`.

**Enhanced form submission (guide §"Enhancing forms with fetch and navigation")**

- Intercept `submit`, call `event.preventDefault()`, and send the form's own action/method with `new FormData(form)` so the controller is unchanged. Pass the event's abort signal into `fetch(...)`; on success follow the action's redirect with `navigate(response.url, { history: "replace" })` (§"Enhancing forms with fetch and navigation"). Non-enhanced submissions must still receive the same redirect/error response. Choose the boundary deliberately: normal submit for a document navigation, `fetch()` when the page needs pending/inline errors before navigating, JSON when a browser-side model owns the data, polling for independent data (§"Enhancing forms with fetch and navigation").
- App seam: the existing submit interception is the **agent/chat stream path**, a different synchronization boundary. `app/assets/streams/public/agent-events-stream.tsx:163-166,229` and `app/assets/streams/public/customer-chat-stream.tsx:50-55,182` `preventDefault()`, build `new FormData(form)`, and hand it to the SSE stream; `app/assets/streams/public/support-agent-stream.tsx:477-480,568` fetches `body: new FormData(form)` and then reloads the frame (`:118`); the former `app/ui/settings-enhance.browser.tsx:256` document-level capture site was deleted with that file (app re-checked 2026-10-14); `app/ui/message-compose.browser.tsx:190-197` still uses form-level `submit` capture for side effects. None follow the guide's `navigate(response.url, { history: "replace" })`. They also attach with native `form.addEventListener('submit', handler, { signal: handle.signal })` (e.g. `agent-events-stream.tsx:229`) — the app convention — rather than `on('submit', ...)`. `new FormData(form)` carries the rendered `_csrf` hidden field (`app/ui/csrf-token-input.tsx`), so interception needs no extra CSRF plumbing.

## When to Use

- You are adding a client-only mount point, custom DOM event, code-driven navigation, link-like non-anchor host, or form interception in a Remix 3 `clientEntry` and want to know which guide section owns it and whether the app already has a seam.
- You are about to copy `createRoot`, the `run()` lifecycle, `navigate`/`link`/`attrs`, `createMixin`/`handle.element`, the `on(...)` handler signal, or the guide's fetch-and-`navigate` form enhancement, and need the app's actual convention first.
- A list's DOM or component state pairs with the wrong row after an insert/reorder/sort, a controlled input fights `defaultValue`, or an enhanced submit must follow a controller redirect.
