# Remix 3 Interactivity Runtime

**Source:** Installed guide `node_modules/remix/guides/05-interactivity.md` (remix 3.0.0-rc.3); §section refs in the text below are to that file. App seams verified against `app/`.

**Extracted:** 2026-09-26

**Context:** Wiring browser interactivity in a Remix 3 `clientEntry`: a client-only root, the `run()` runtime lifecycle, custom event mixins, cancellation granularity, optimistic/pending ownership, `navigate`/`link`/`attrs`, list keys and input ownership, and enhanced form submission. This reference points at the guide and records only the app-specific seams and disambiguations the guide cannot know.

## Problem

The guide covers the runtime and mixin APIs completely, but this app has its own client wiring (`app/assets/entry.tsx`, `app/assets/error-card.browser.tsx`) and its own shared handler conventions that diverge from the guide's examples in ways that are easy to misread: `createRoot` is used for a fatal-error takeover rather than a widget; no code imports `navigate` from `remix/component` (frame navigation is a local `navigateFrame` helper in `lists-client.tsx`); the existing form interception is the SSE/JSON stream path, not the guide's fetch-and-redirect enhancement; and no app code uses the `on(...)` per-handler signal, `createMixin`, `link()`, or `attrs()`. Treating any of these as "already implemented like the guide" leads to wrong edits.

## Solution

**Client-only root — `createRoot(container)` (guide §"Mount client-only UI with createRoot")**

- The root owns its container. `root.render(node)` schedules a tree, `root.flush()` applies pending work synchronously, and `root.dispose()` removes the tree and runs cleanup; the guide's widget example disposes on `pagehide` with `{ once: true }` (§"Mount client-only UI with createRoot"). Reserve `createRoot` for UI with no server-rendered component to hydrate; normal page UI starts on the server via `clientEntry(...)` so users are not left waiting on JavaScript (§"Mount client-only UI with createRoot").
- App seam: the only `createRoot` in the app is the fatal-error takeover — `renderFatalError()` in `app/assets/error-card.browser.tsx:113-135` calls `createRoot(document.body).render(<ErrorCard .../>)`. It runs from `run()`'s error listener (`app/assets/entry.tsx:44-56`) **after** `app.dispose()` and after `fadeOutBody()` clears `document.body`, so the root replaces the whole document. It never registers the guide's `pagehide` dispose (the runtime it could outlive is already gone) and never calls `root.flush()`/`root.dispose()` itself. A future non-fatal client-only root (a widget in a page shell) is new behavior: copy the guide's `pagehide` dispose, not the error card's terminal pattern.

**Browser runtime lifecycle — `run()` (guide §"Booting the browser runtime with run")**

- `app.ready()` resolves after the initial client entries hydrate. `app.flush()` synchronously applies pending component updates — the supported way to observe the DOM immediately, scoped by the guide to tests and integrations. `app.dispose()` removes the runtime's components and listeners (§"Booting the browser runtime with run").
- App seam: `app/assets/entry.tsx:11-12` keeps the `run()` result in module `app`, but nothing in `app/` calls `app.ready()` or `app.flush()` (verified). The single lifecycle call is `app.dispose()` in the error listener at `:44-45`, immediately before the error card mounts. There is no production or test seam that waits on `ready()`; the app relies on `app.addEventListener('error', ...)` (`:44`) for failure handling, and `remix3-testing` owns how tests drive client DOM without `app.flush()`.

**Custom event mixin — `createMixin` + `handle.element` (guide §"When to create a custom event mixin")**

- Build the interaction from low-level events in setup scope, then dispatch one semantic typed event (`LongPressEvent extends Event` with `{ bubbles: true }`) that consumers attach with `on(...)`. `handle.addEventListener("insert"|"remove", ...)` is the **mixin handle's** own lifecycle events (not a DOM `addEventListener`): `insert` supplies `event.node`, `remove` is the cancel hook. The mixin returns `<handle.element mix={[...]} />`. Augment `HTMLElementEventMap` in a `declare global` block so the consumer's `on(longPressType, ...)` is typed, and namespace the name (`app:longpress`) to avoid collisions (§"When to create a custom event mixin").
- App seam: none. `createMixin` and `handle.element` do not appear in `app/` (verified). Reusable behavior in this app is currently `on(...)` in mixin arrays plus imperative `ref` callbacks and helper modules (`app/ui/mixins/icon.ts`, `app/ui/auto-grow-textarea.ts`); no custom DOM events are dispatched outside tests, which dispatch native `submit`/`input` (e.g. `app/assets/streams/streams.test.browser.tsx:91`). A custom event mixin would be the first in the repo — follow the guide and the `remix/component` API overview (`node_modules/remix/src/component/README.md`), not an app precedent.

**Cancellation granularity (guide §"State, updates, and post-render tasks", §"Async work and cancellation")**

- `handle.update()` schedules work and its promise resolves to an `AbortSignal`, but the runtime **cannot** abort it between `await handle.update()` and the next synchronous statement — `input.focus()` needs no check. Capture the signal only when more async work follows: pass it to `fetch(href, { signal })` and re-check `signal.aborted` after each later `await` before touching state (§"State, updates, and post-render tasks"). The second argument of an `on(type, (event, signal))` handler (§"Async work and cancellation") is the signal for work where the latest event should replace earlier work; it aborts on re-run **or** element removal. The `queueTask` and `handle.signal` aborts are already covered by `references/queuetask-over-raf.md` and `remix3-frame-cliententry` and are not restated here.
- App seam: no app handler uses the `on(...)` second-arg signal (verified — no `(event, signal)`/`(e, signal)` handlers). The app cancels async work with `handle.signal` on native listeners (e.g. `app/assets/streams/public/agent-events-stream.tsx:407,414-416`), a local `AbortController` (`app/actions/lists/public/list-name-edit.tsx:47-49`), or the signal returned by `handle.frame.reload()` (`app/actions/client/public/grid-refresh-button.tsx:45-50`). When you attach with native `addEventListener` — because the target is outside the render tree or you are inside a `queueTask` — you do not get the per-handler signal; pass your own controller or `handle.signal`, as those sites do.

**Pending and optimistic UI ownership (guide §"Pending and optimistic UI")**

- Pending state that the render reads (disabled controls, pending labels, progress, duplicate-submit prevention) belongs in setup scope and is set/cleared around the request (§"Pending and optimistic UI"). Optimistic UI — rendering the expected result before the request settles — belongs in the model that owns the data, together with its recovery policy: restore the previous state or adopt the server response on failure, and let the component render the resulting error/retry (§"Pending and optimistic UI"). Use optimistic only for reversible, predictable changes; wait for the response when the server chooses the final value, performs something destructive, or can reject in a way the user must resolve first (§"Pending and optimistic UI").
- App seam: no optimistic state exists in `app/` (`optimistic` and `extends TypedEventTarget` have no matches). The only client request state is pending/disabled in setup scope or entry-local flags — `pending` in `app/actions/client/public/grid-refresh-button.tsx:32`, `submitting` in `app/assets/streams/public/support-agent-stream.tsx:773-774`, `setFormEnabled(false)` in `app/assets/streams/public/agent-events-stream.tsx:316`. Adopting optimistic UI means creating the model home the guide requires; do not park optimistic state in the entry just because pending state lives there.

**`navigate()`, `link()`, and `attrs()` (guide §"Client navigation", §"Composing behavior with mix")**

- `navigate(href, options)` is for navigation that begins in code. `link(href, options)` makes a non-anchor host behave like a link: it adds `role="link"`, makes the host keyboard-focusable when needed, handles Enter and mouse/modifier-key activation, and reflects a disabled host with `aria-disabled` (§"Client navigation"). Prefer a real anchor when the markup fits. `attrs(...)` supplies default attributes without replacing explicit element props (§"Composing behavior with mix").
- App seam: no code imports `navigate` from `remix/component`; `app/ui/appointment-sidebar.tsx` (formerly `appointment-sidebar.browser.tsx`) is now server-rendered and imports no `navigate` (app re-checked 2026-10-14). **Disambiguation:** `app/actions/lists/public/lists-sidebar-keyboard.tsx:63` drives frame navigation directly with `handle.frame.reload({ src: href })` (previously `frame.src = href; frame.reload()`) — that is frame navigation, not the `remix/component` `navigate()`. Grep hits for `navigate(` are not all client navigation. The `link()` and `attrs()` mixins do not appear in `app/` (the only `attrs` hits are the server's `data-rmx-preserve-attrs`; the only `link` hits are a theme color token and JSDoc). The closest hand-rolled pattern is the disabled pagination `<span aria-disabled="true">` in `app/ui/admin-report1-page.tsx:337,346`, which is not focusable and not a `link()`; adopting either mixin is new.

**Stable list keys and controlled vs uncontrolled inputs (guide §"State, updates, and post-render tasks", §"Controlled and uncontrolled inputs")**

- Key a list by a stable id whenever an update can reorder/insert/remove items — not by array index or a value created during render — so matching keys move existing DOM/component instances instead of pairing state with the wrong item (§"State, updates, and post-render tasks"). An uncontrolled input keeps its value in the DOM and `defaultValue` is only its initial value; a controlled input takes `value` from state, and its `input` handler copies the DOM value into that state before `handle.update()` (§"Controlled and uncontrolled inputs").
- **Failure mode the guide does not state:** a controlled `value={...}` input whose handler updates state but **omits `handle.update()`** does not just go stale — `@remix-run/component` attaches a controlled-reflection `input`/`change` listener (`ensureControlledReflection`, `restoreControlledReflections` in `reconcile.ts:133,201`) that *restores the DOM value toward the last-rendered value* on every event. So the field snaps back mid-typing: the user can't compose text and a picked value "vanishes" until some unrelated render syncs it. The symptom reads as **"adding tags/date is very slow / never shows up"** — check for a missing `handle.update()` (or an accidental controlled `value=`) before suspecting render cost. **`<select>` is exempt from the `input`-path restore** (`shouldRestoreControlledReflectionOnInput` → `node.type === 'select'` returns false, `reconcile.ts:121-129`), which is why a select-only control looked fine while sibling `value=` date/text inputs broke; its `change` handler must still re-render, and on a *reused* node assert `el.value` in a `ref` callback (diffProps skips when `prev === next` and only sets the `value` *property* on change).
- App seam: `defaultValue={...}` is the app's norm for filters/forms (e.g. `app/ui/lists-layout.tsx:310`), and `app/ui/dirty-form-guard.browser.tsx:29-42` explicitly treats the live `defaultValue` as the server-rendered baseline. The lists inline row editor is the cautionary example of the failure mode: it rendered date/tags as controlled `value={editDue}`/`value={editTags}` with `setEditDue`/`setEditTags` setters that never re-rendered, so typed input was reverted. It is now **uncontrolled** — `defaultValue={editDue}` / `defaultValue={editTags}` plus a mount-`ref` asserting `el.value = editPriority` for the select (`app/actions/lists/public/lists-view.tsx:1273-1335`), mirroring the label field. The year/resource `<select>` controls in `app/ui/appointment-sidebar.tsx:68,78` are now server-rendered (`selected={res.id === selectedResourceId}` at `:70`, `selected={y === year}` at `:80`), not controlled client inputs (app re-checked 2026-10-14). Guard: `app/actions/lists/public/lists-meta-inputs.test.browser.tsx` — types tags and sets a date with no re-render, asserts the DOM keeps them and the commit payload is verbatim. Index keys still exist on message lists (`key={i}` in `app/ui/customer-chat-page.tsx:104`, `key={index}` in `app/ui/support-agent-page.tsx:354`); that is fine for static markup, but do not copy it for a list that streams, reorders, or inserts (§"State, updates, and post-render tasks").

**Enhanced form submission (guide §"Enhancing forms with fetch and navigation")**

- Intercept `submit`, call `event.preventDefault()`, and send the form's own action/method with `new FormData(form)` so the controller is unchanged. Pass the event's abort signal into `fetch(...)`; on success follow the action's redirect with `navigate(response.url, { history: "replace" })` (§"Enhancing forms with fetch and navigation"). Non-enhanced submissions must still receive the same redirect/error response. Choose the boundary deliberately: normal submit for a document navigation, `fetch()` when the page needs pending/inline errors before navigating, JSON when a browser-side model owns the data, polling for independent data (§"Enhancing forms with fetch and navigation").
- App seam: the existing submit interception is the **agent/chat stream path**, a different synchronization boundary. `app/assets/streams/public/agent-events-stream.tsx:304-327` and `app/assets/streams/public/customer-chat-stream.tsx:815-846` `preventDefault()`, build `new FormData(form)`, and hand it to the SSE stream; `app/assets/streams/public/support-agent-stream.tsx:784-788` fetches `body: new FormData(form)` and then reloads the frame (`:813`); the former `app/ui/settings-enhance.browser.tsx:256` document-level capture site was deleted with that file (app re-checked 2026-10-14); `app/ui/message-compose.browser.tsx:101` still uses document-level `submit` capture for side effects. None follow the guide's `navigate(response.url, { history: "replace" })`. They also attach with native `form.addEventListener('submit', handler, { signal: handle.signal })` (e.g. `agent-events-stream.tsx:407`) — the app convention — rather than `on('submit', ...)`. `new FormData(form)` carries the rendered `_csrf` hidden field (`app/ui/csrf-token-input.tsx`), so interception needs no extra CSRF plumbing.

## When to Use

- You are adding a client-only mount point, custom DOM event, code-driven navigation, link-like non-anchor host, or form interception in a Remix 3 `clientEntry` and want to know which guide section owns it and whether the app already has a seam.
- You are about to copy `createRoot`, the `run()` lifecycle, `navigate`/`link`/`attrs`, `createMixin`/`handle.element`, the `on(...)` handler signal, or the guide's fetch-and-`navigate` form enhancement, and need the app's actual convention first.
- A list's DOM or component state pairs with the wrong row after an insert/reorder/sort, a controlled input fights `defaultValue`, or an enhanced submit must follow a controller redirect.
