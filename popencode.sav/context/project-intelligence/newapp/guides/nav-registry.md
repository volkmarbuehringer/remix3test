# Guide: Nav Registry Pattern

**Core Idea**: Navigation is driven by a typed data array (`NAV_SECTIONS`) defined in a single file. Adding a page to the nav means adding one entry to the array — no template editing, no layout changes.

---

## The Registry

`app/ui/nav.ts` defines the contract:

```tsx
export type NavItem = {
  label: string
  href: string
  icon?: string        // Optional
  adminOnly?: boolean  // Optional — hides from non-admin users
}

export type NavSection = {
  id: string
  label?: string      // Optional section heading (rendered as uppercase label)
  items: NavItem[]
}

export const NAV_SECTIONS = [
  {
    id: 'pages',
    label: 'Pages',
    items: [
      { label: 'Home', href: '/' },
      { label: 'AI', href: '/ai' },
      { label: 'Admin', href: '/admin', adminOnly: true },
    ],
  },
  {
    id: 'showcase',
    label: 'Showcase',
    items: [
      { label: 'Overview', href: '/ui' },
      // Dynamic entries from SHOWCASE_SECTIONS + SHOWCASE_PAGES:
      ...SHOWCASE_SECTIONS.flatMap((section) =>
        section.pageIds.map((id) => ({
          label: SHOWCASE_PAGES[id].navLabel ?? SHOWCASE_PAGES[id].label,
          href: SHOWCASE_PAGES[id].path,
        })),
      ),
    ],
  },
] as const satisfies readonly NavSection[]
```

## How It Works

1. **Layout reads** `NAV_SECTIONS` and renders nav links grouped by section
2. **Section headings** rendered when `section.label` is present
3. **`adminOnly` filtering**: Items with `adminOnly: true` are hidden from non-admin users via `.filter(item => !item.adminOnly || user?.role === 'admin')`
4. **Showcase items are dynamic**: Showcase nav links are generated by iterating `SHOWCASE_SECTIONS` and `SHOWCASE_PAGES` — adding a showcase section/entry auto-adds nav items
5. **Active state** computed via `currentPath` matching (exact match or prefix + `/`)
6. **Adding a page** = one array entry, no template changes

Layout rendering (from `app/ui/layout.tsx`) — renders sections as groups with visual dividers:

```tsx
<nav mix={navStyle}>
  {NAV_SECTIONS.map((section) => (
    <div key={section.id} mix={navSectionGroupCss}>
      {section.label ? (
        <span mix={navSectionLabelCss}>{section.label}</span>
      ) : null}
      {section.items
        .filter(item => !item.adminOnly || user?.role === 'admin')
        .map((item) => (
        <a
          key={item.href}
          href={item.href}
          mix={[navLinkStyle, isActive(item.href) ? navActiveStyle : null].filter(Boolean)}
        >
          {item.label}
        </a>
      ))}
    </div>
  ))}
</nav>
```

Section group styling adds a left border between groups:

```tsx
const navSectionGroupCss = css({
  display: 'flex',
  alignItems: 'center',
  gap: theme.space.xs,
  '& + &': {
    borderLeft: `1px solid ${theme.colors.border.subtle}`,
    paddingLeft: theme.space.md,
  },
})

const navSectionLabelCss = css({
  fontSize: theme.fontSize.xxs,
  fontWeight: theme.fontWeight.semibold,
  letterSpacing: theme.letterSpacing.meta,
  textTransform: 'uppercase',
  color: theme.colors.text.muted,
  marginRight: theme.space.xs,
})
```

## Adding a Nav Item

```tsx
export const NAV_SECTIONS = [
  {
    id: 'pages',
    label: 'Pages',
    items: [
      { label: 'Home', href: '/' },
      { label: 'New Page', href: '/new' },  // ← add here
      { label: 'Admin Only', href: '/admin', adminOnly: true },  // ← hidden from users
    ],
  },
] as const satisfies readonly NavSection[]
```

For **showcase nav items**, don't edit `nav.ts` directly — add the page to `SHOWCASE_PAGES` + `SHOWCASE_SECTIONS` in `showcase-registry.ts` instead. The nav items auto-generate.

## The `adminOnly` Flag

The `adminOnly` flag controls visibility by user role:

```tsx
// In layout.tsx:
items.filter(item => !item.adminOnly || user?.role === 'admin')
```

Scenarios:
- `adminOnly: true` + admin user → visible
- `adminOnly: true` + non-admin user → hidden
- `adminOnly: false` or omitted → visible to all
- No user (not logged in) → `user` is `null`, so `adminOnly` items are hidden

This avoids duplicating route-level auth checks for nav visibility. The `/admin` route itself is still protected by `requireAuth() + requireAdmin()` middleware — the flag only controls the nav link.

## Nav Consolidation Strategy

Recent consolidation moved **Lists** and **Client Lab** from the main navbar to the admin dashboard cards and sidebar:

| Page | Former Location | Current Location |
|------|----------------|-----------------|
| Lists | Main nav bar (`/lists`, `/lists/:id`) | Admin sidebar ("Data" group) |
| Client Lab | Main nav bar (`/client`) | Admin sidebar ("Data" group) |
| AI | Admin only | Main nav bar (`/ai`) |
| Home, Showcase | Main nav bar | Main nav bar (unchanged) |

**Decision rule**: Main navbar shows top-level app sections (Home, AI, Admin). Feature-specific pages live in the section's own navigation (Admin sidebar, AI sidebar, etc.).

## Active State Logic

```tsx
let isActive = (path: string) => {
  if (!currentPath) return false
  return currentPath === path || currentPath.startsWith(path + '/')
}
```

This means:
- `currentPath = '/ui'` matches `href = '/ui'` (exact)
- `currentPath = '/ui/button'` matches `href = '/ui'` (prefix + `/`)
- `currentPath = '/user'` does NOT match `href = '/ui'` (no prefix match)

## as const satisfies

The `as const satisfies readonly NavSection[]` assertion gives:
- **Type safety**: Items must conform to `NavSection[]`
- **Literal types**: `href` values retain literal string types (not just `string`)

## When to Extend

Add a new `NavSection` when the nav needs a visual divider + heading (e.g., "Admin", "Settings"). Use the existing `pages` section for general pages. Don't create a section for a single item — just add it to an existing section.
