# Database review — 2026-11-03

Scope: the full `public` schema, the migration chain, and every non-test data-access
module under `app/data/`, `app/utils/` and the Mastra workflows/tools.
Prior reviews: 2026-09-24 (`db/manual-migrations/2026-09-24-db-review-fixes.sql`) and
2026-09-28 (`2026-09-28-db-review-indexes.sql`); deferred items are tracked in
[`docs/db-type-migration-runbook.md`](docs/db-type-migration-runbook.md).

Method: read the live catalog (`pg_class`, `pg_constraint`, `pg_index`, `pg_stat_*`,
`pg_settings`) and the code, then confirmed query behaviour with `EXPLAIN (ANALYZE,
BUFFERS)` against a 50 000-row synthetic fixture inserted inside a transaction and rolled
back (`lists` was `VACUUM (ANALYZE)`d afterwards; `n_dead_tup` is back to 0).

Live environment: PostgreSQL **18.3** (not 18.6 as the runbook's compatibility note says),
190 MB database — 104 MB app tables (66 MB of it `uploads` BYTEA) and 89 MB of `mastra_*`
tables, all in `public`.

## Verdict

The _query and transaction_ layer is in better shape than most codebases this size: the
double-booking constraint is a real database constraint, the read-modify-write paths take
row locks in id order, every user-supplied value is parameterized, and every foreign key
has a leading index (audited: zero misses). The gaps are **operational** — the database
has no backups, no query observability, and one deploy habit that silently destroys
uploaded files.

## P1 — fix before the next production deploy

### 1. Redeploy deletes all filesystem uploads, then the sweep deletes the evidence

`UPLOAD_FILES_DIR` is unset in `.env` (verified), so it resolves to `tmp/uploads` —
[app/storage.ts:30](app/storage.ts#L30) — inside the container's writable layer. The code
already says so at [app/storage.ts:19-21](app/storage.ts#L19-L21): _"the default lives
inside the container's writable tmp/ directory ... and is therefore ephemeral across
container replacements."_

Neither deployment path mounts a volume for it:
[docker-compose.yml:10-12](docker-compose.yml#L10-L12) mounts only the TLS key and cert,
and [docker.sh](docker.sh) does `docker rm -f newapp` on every deploy.

The result is worse than lost bytes: `deleteRowsMissingFiles`
([app/data/upload-files-sweep.ts:194-235](app/data/upload-files-sweep.ts#L194-L235)) treats
the filesystem as the authority and **deletes the `upload_files` row when its `.dat` is
missing**. So one hour after a redeploy the database no longer shows that the files ever
existed — no failed download, no error page, just empty rows.

Fix (pick one):

- Mount a named volume or host path in both deploy paths:
  ```yaml
  volumes:
    - uploads:/app/tmp/uploads
    - sessions:/app/tmp/sessions # otherwise every redeploy logs everyone out
  ```
- Or move the bytes to object storage / back into the DB and retire the disk path.

Either way, make the sweep defensive: if a pass finds _all_ published pairs missing, that
is a mount failure, not an orphan set. Abort and log loudly instead of deleting rows.

### 2. No backup or point-in-time recovery

`archive_mode = off`, `archive_command = (disabled)`, `wal_level = replica`. Nothing in
`scripts/`, `.github/` (`ci.yml.disabled`) or the deploy files runs `pg_dump` or
`pg_basebackup`. The database holds password hashes, `audit_logs` (the audit trail the app
deliberately keeps for 90 days), chat transcripts and 66 MB of BYTEA uploads that exist
nowhere else.

Minimum: a nightly `pg_dump -Fc` to off-host storage plus a documented, _tested_ restore.
If the retention windows in [app/data/maintenance.ts:17-23](app/data/maintenance.ts#L17-L23)
are the data-loss policy, say so explicitly; today a lost volume is unrecoverable.

## P2 — fix this cycle

### 3. There is no way to find the next slow query

`pg_stat_statements` is not installed (`shared_preload_libraries` is empty),
`log_min_duration_statement = -1`, `track_io_timing = off`. Every performance claim in
this document had to be re-derived from `EXPLAIN`; nothing historical is available.

```conf
shared_preload_libraries = 'pg_stat_statements'   # requires restart
pg_stat_statements.track = all
log_min_duration_statement = 500ms
track_io_timing = on
idle_in_transaction_session_timeout = 60s          # currently 0 (forever)
```

The app pool already sets `statement_timeout: 30000`
([app/db.ts:23-29](app/db.ts#L23-L29)), which bounds any single statement issued by the app
(but not by `psql` or the migration CLI). `idle_in_transaction_session_timeout = 0` is the
remaining hole: a leaked idle transaction pins the oldest xmin and blocks vacuum
indefinitely, and no timeout will ever close it.

### 4. The booking exclusion constraint rests on an unenforced invariant

`no_overlapping_seats` excludes on `(resource_id, date, during)`
([db/migrations/20261101000000_baseline/up.sql:112-116](db/migrations/20261101000000_baseline/up.sql#L112-L116)).
That is correct geometry — but only if `date` is exactly UTC midnight. If a writer passes
`Date.now()`, two appointments on the same day get different `date` values and the
constraint stops seeing them as conflicting. Today all 19 rows are aligned (`date % 86400000
= 0` for every row), but nothing in the database enforces it.

**I tried to add the `CHECK` and reverted it**, which turned out to be the useful result:
the constraint immediately failed 34 tests, and not only because fixtures were sloppy.
The invariant genuinely does not hold across the write paths yet:

- [app/actions/mastra/workflows/customer-booking-workflow.ts:83](app/actions/mastra/workflows/customer-booking-workflow.ts#L83)
  and [booking-workflow.ts:14](app/actions/mastra/workflows/booking-workflow.ts#L14) accept
  `date: z.number()` from tool input and pass it straight to
  `createAppointmentRecord(dayMs: inputData.date)` — no day normalisation anywhere on
  that path. An agent that supplies an ISO timestamp books a row with a non-midnight
  `date`, and the exclusion constraint silently stops protecting that day.
- ~30 test fixtures insert `Date.now()` as `date`/`day`
  (e.g. [app/data/pdf.test.ts:21-27](app/data/pdf.test.ts#L21-L27),
  [app/data/offerings-queries.test.ts:183-188](app/data/offerings-queries.test.ts#L183-L188)),
  so the suite encodes the same wrong model.

Correct order — and the reason this is a follow-up rather than a drive-by migration:

1. Normalise at every write boundary: truncate `date` to UTC midnight in
   `createAppointmentRecord` (or validate the workflow's `date` input against
   `date % 86400000 === 0` and reject otherwise).
2. Fix the fixtures to use `getTodayUtcMidnight()` and friends, so the tests model real
   rows.
3. _Then_ add `CHECK (date % 86400000 = 0)` and `CHECK (day % 86400000 = 0)` with
   `NOT VALID` + `VALIDATE` — one migration each, or both in one if the file stays
   multi-statement-safe (plain DDL is fine).

Better still, make `date` a real `date` column (runbook item B): that removes the
invariant, the epoch arithmetic and this whole class of bug.

### 5. Production boots run a demo seed, and `clients` cannot protect itself

`initializeAppDatabase()` calls `seed()` on every boot
([app/db.ts:66-77](app/db.ts#L66-L77)). On an empty database that creates 2 login accounts,
3 messages, **200 demo clients** and demo resources/offerings
([app/data/seed.ts:82-105](app/data/seed.ts#L82-L105)).

- `clients` has **no constraints beyond the primary key** and **no indexes at all**
  (verified against `pg_constraint`/`pg_indexes`) — no unique email, free-text `role` and
  `status`. The 200-row insert is guarded only by `COUNT(*) = 0`, so two instances booting
  concurrently can both pass the check and write 400 rows.
- The two "normalize legacy rows" statements
  ([app/data/seed.ts:110-132](app/data/seed.ts#L110-L132)) run a regex
  (`email ~ '^user[0-9]+@example[.]com$'`) with no supporting index on every single boot.

Recommendation: make the seed opt-in (`SEED_DEMO_DATA=1`) and out of the boot path;
keep only the admin-bootstrap user. If the demo rows must stay, take a short advisory lock
around `seed()` so concurrent boots serialize.

### 6. The lists grid's search predicate cannot use any index

[app/data/lists.ts:176-183](app/data/lists.ts#L176-L183) (and the same predicate twice more
at lines 261-266 and 281-286 for the sidebar and its `COUNT(*)`):

```sql
WHERE (title ILIKE $1 OR description ILIKE $1
       OR EXISTS (SELECT 1 FROM jsonb_array_elements(list) item
                  WHERE item->>'label' ILIKE $1))
```

The first two branches are covered by `idx_lists_title`/`idx_lists_desc` (GIN trgm, both
live and usable — confirmed via a forced `BitmapOr` plan). The third branch is a set-returning
function per row, so the whole `OR` degrades to a scan with the subplan executed once per
row.

Measured at 50 000 rows (warm cache):

| Variant                                  | Plan                                          | Time        |
| ---------------------------------------- | --------------------------------------------- | ----------- |
| with the `jsonb_array_elements` branch   | index scan + filter, **50 025** subplan calls | **73.8 ms** |
| two-column search only, seqscan disabled | `BitmapOr` over both trgm indexes             | **1.3 ms**  |

At today's 25 rows the whole query is 0.46 ms, so this is not urgent — but it grows
linearly with `lists`, and the sidebar's `COUNT(*)` replays the same predicate a second
time per request.

Options, cheapest first:

1. Accept it and cap the searchable corpus (document the ceiling).
2. Search items only on demand (a separate "search inside lists" action) so the grid's
   default query keeps its trigram path.
3. Normalize items into a `list_items` table with a trigram index — the durable fix, and
   it also makes merge/move atomic SQL instead of JSON read-modify-write.

## P3 — opportunistic

**7. Global upload quota is an unlocked full scan.** `sumUploadFileBytes()`
([app/data/upload-files.ts:173-180](app/data/upload-files.ts#L173-L180)) runs
`SELECT SUM(size) FROM upload_files` on every upload. Unlike the per-user check, it is
**not** inside the `pg_advisory_xact_lock` transaction
([app/data/upload-files.ts:115-132](app/data/upload-files.ts#L115-L132)), so concurrent
uploads can jointly cross `UPLOAD_FILES_QUOTA_BYTES`. A covering index
`(uploaded_by) INCLUDE (size)` makes the per-user sum index-only; the global sum wants a
counter row (or the same advisory lock on a global key).

**8. `users.email` uniqueness is case-sensitive.** The table hook lowercases on every write
([app/data/schema.ts:81-83](app/data/schema.ts#L81-L83)), so the app is consistent — but any
raw-SQL or seed path can create `Admin@x` next to `admin@x`. Add
`CREATE UNIQUE INDEX CONCURRENTLY users_email_lower_uidx ON users (lower(email));`
(remember `-- data-table/transaction: none` for `CONCURRENTLY`).

**9. Collation drift.** The server logs on every connection:
_"database was created with collation version 2.43 but the OS has 2.44"_. Run
`ALTER DATABASE newapp REFRESH COLLATION VERSION;` and reindex text indexes if the ordering
changed. Also correct the runbook's "live database is 18.6" note — it is 18.3.

**10. Two upload systems.** `uploads` (BYTEA, 66 MB / 87 rows) and `upload_files`
(filesystem metadata) have separate quota env vars, separate retention paths and separate
grids. Retention already deletes BYTEA rows after 90 days, which no user asked to be
deleted implicitly. Pick one store and retire the other.

**11. Hygiene.** `data_table_migrations` still exists and is deliberately ignored
([app/db.ts:39-47](app/db.ts#L39-L47)) — drop it so nobody reads it. `webhook_requests.id`
uses `gen_random_uuid()` ([baseline:233](db/migrations/20261101000000_baseline/up.sql#L233));
PostgreSQL 18 is installed and `uuidv7()` works here, so the runbook's one-line fix is
available. All ~200 `mastra_*` tables sit in `public` next to app tables (89 MB of 190 MB);
a dedicated `mastra` schema and role would keep vendor DDL away from app data.

**12. Small concurrency notes.** `runDatabaseMaintenance` is fired by `setInterval` with no
in-flight guard ([app/data/maintenance.ts:169-176](app/data/maintenance.ts#L169-L176)); a
sweep slower than the interval stacks. `pg_advisory_xact_lock($1::bigint)` with the raw
`userId` (three call sites) occupies the un-namespaced lock space — a future
`pg_advisory_xact_lock(42)` elsewhere would collide. Use the two-int form
`pg_advisory_xact_lock(namespace, user_id)`.

## What is solid — do not churn it

- **Double-booking is prevented by the database**, not by a check-then-insert:
  `EXCLUDE USING GIST (resource_id WITH =, date WITH =, during WITH &&)` plus an
  `int4range` bounds `CHECK`, with `23P01` mapped to a typed conflict
  ([app/utils/db-errors.ts:35-44](app/utils/db-errors.ts#L35-L44)).
- **Lock ordering is correct.** `moveItemsBetweenLists` locks both rows
  `toSorted((a, b) => a - b)`
  ([app/data/lists.ts:786-800](app/data/lists.ts#L786-L800)); the last-admin guard locks
  admin rows `ORDER BY id FOR UPDATE` before counting
  ([app/actions/admin/users/controller.tsx:691-702](app/actions/admin/users/controller.tsx#L691-L702)).
- **Optimistic concurrency** via an `expectedUpdatedAt` predicate that is re-checked in the
  `UPDATE`'s `WHERE` ([app/data/lists.ts:411-422](app/data/lists.ts#L411-L422)).
- **All SQL is parameterized.** Identifiers that cannot be parameters come from fixed
  whitelists (`SORT_EXPRS` in [app/data/admin-lists.ts:80](app/data/admin-lists.ts#L80),
  `ADMIN_ORDER_BY_COLUMNS`, the maintenance table/key unions).
- **Every foreign key has a leading index** (audited against `pg_constraint`; zero misses).
- **Quota admission is serialized** per user with an advisory lock and a transaction
  ([app/data/uploads.ts:281-316](app/data/uploads.ts#L281-L316)).
- **Retention is batched** with a per-tick cap so a backlog cannot hold one long
  transaction ([app/data/maintenance.ts:52-82](app/data/maintenance.ts#L52-L82)).
- **Migrations are checksummed, advisory-locked and append-only**, with an idempotent
  baseline and a documented expand/contract deploy path (`db/migrations/README.md`).
- **Partial and trigram indexes are used where they can be**: unread-notification partial
  index, `webhook_requests` payload expression index, trgm on every `ILIKE`-able column.

## Implemented — 2026-11-03

Five migration directories, all applied and verified (`npm run db:status` shows every row
`applied`, nothing pending or missing):

| Migration                                          | Change                                                            |
| -------------------------------------------------- | ----------------------------------------------------------------- |
| `20261103120100_users_email_lower_unique`          | `users_email_lower_uidx` on `lower(email)` (P3 #8)                |
| `20261103120200_webhook_requests_uuidv7`           | `id` default `gen_random_uuid()` → `uuidv7()` (P3 #11)            |
| `20261103120300_upload_files_quota_index`          | `(uploaded_by) INCLUDE (size)` covering index (P3 #7)             |
| `20261103120400_drop_redundant_upload_files_index` | drops the now-superseded plain btree                              |
| `20261103120500_archive_legacy_migration_journal`  | `data_table_migrations` → `data_table_migrations_legacy` (P3 #11) |

Deviations from the plan above:

- **P2 #4 is not in this batch.** The midnight `CHECK` was written, applied, and rolled
  back after it failed 34 tests and exposed unnormalised `date` inputs on the Mastra
  booking workflows. It needs the write-boundary fix first — see the revised finding #4.

- **Renamed, not dropped.** `data_table_migrations` held one row
  (`20260724000001 create_all`, applied 2026-07-24) — the only record that the pre-runner
  bootstrap ran. Renaming keeps that audit trail (same reason `db/manual-migrations/` is
  kept) while making the live journal unambiguous. The guards make it a no-op on a fresh
  database.
- **Five migrations, not four.** `CREATE INDEX CONCURRENTLY` cannot share a file with any
  other statement: with `-- data-table/transaction: none` the runner sends the file as one
  query string, which PostgreSQL executes as an implicit transaction block and rejects.
  The first attempt failed exactly this way, so the quota index and the redundant-index
  drop became two migrations. The rule is now documented in
  [`db/migrations/README.md`](db/migrations/README.md#L23-L29).

Still outside the runner (needs superuser / restart): `ALTER DATABASE newapp REFRESH
COLLATION VERSION;` (P3 #9) and the `postgresql.conf` changes from P2 #3. The P1 items are
configuration, not migrations: a volume mount and a backup job.
