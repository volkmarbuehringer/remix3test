## Context

The starter app was generated by `remix new` and contains a single home page with inline CSS, no theme system, no reusable component styles, and a single hardcoded nav link. All five target patterns (theme system, mixin namespaces, page primitives, nav registry, component showcase) coexist in the `@remix-run/ui` demo at `~/remix/packages/ui/demo/` and the bookstore at `~/alpha4/my_app/`. The design below adapts those patterns to a fresh app that will grow from 1 to many pages.

## Goals / Non-Goals

**Goals:**

- Add a `createTheme()`-based theme system with light and dark mode that compiles to CSS custom properties
- Create namespace-exported mixin modules for common component styles (button, card, input, text)
- Create shared page layout primitives (PageSection, ShowcaseLinkCard, CSS constants)
- Add a data-driven nav registry so adding a page updates navigation automatically
- Add a `/ui` component showcase route for documentation and visual reference
- Refactor all existing files to consume the theme via semantic tokens
- Preserve the existing home page content and all current functionality

**Non-Goals:**

- No changes to the Remix framework itself
- No CSS-in-JS library changes (stays with `remix/ui`'s `css()` tagged template)
- No new external dependencies (uses `remix/ui/theme` which is already available)
- No database, auth, or API changes — UI layer only
- No production deployment configuration

## Decisions

### 1. Custom theme vs. RMX_01 preset

**Decision**: Use a custom `createTheme()` with the same token shape as RMX_01 but with the starter's current color palette, then layer a dark variant.

**Rationale**: The starter's scaffold page already has a specific color scheme (blues, grays, JetBrains Mono font). Switching entirely to RMX_01's palette would change the visual identity. Using `createTheme` with custom values keeps the starter's look while adopting the architecture. The token contract (`theme.space.md`, `theme.surface.lvl0`, etc.) is identical either way, so the mixins and primitives work identically.

**Alternative considered**: Import `RMX_01` from `@remix-run/ui/theme` directly. Rejected because it adds a dependency and changes the starter's visual identity.

### 2. Mixin namespace shape

**Decision**: Each mixin module exports a single named object (e.g., `export const button = { base, primary, ghost, danger }`) rather than flat exports or a barrel index.

**Rationale**: Flat exports (`export const buttonBase`, `export const buttonPrimary`) require the consumer to know every export name in advance. A namespace object enables `import { button } from '...'` then `button.` → autocomplete shows all variants. This matches the `import * as popover from '@remix-run/ui/popover'` pattern from the UI demo, adapted for app-level mixins.

### 3. Nav registry location and shape

**Decision**: A single `app/ui/nav.ts` module exports typed arrays of `NavSection` and `NavItem`. The layout imports this array and renders nav links from it.

**Rationale**: A single file serves as the app's table of contents. Adding a page means appending one entry — the nav renders automatically, active state is handled by a shared `NavLink` pattern, and sections group related pages. The bookstore's `NAV_GROUPS` and the UI demo's `NAV_SECTIONS` both validate this approach.

### 4. Showcase route structure

**Decision**: A `app/actions/ui/controller.tsx` handles `/ui` routes with individual page modules in `app/actions/ui/pages/`. Pages are mapped via a simple object registry.

**Rationale**: The showcase is a self-contained feature that follows the same route ownership pattern the AGENTS.md recommends ("Add `app/actions/<route-key>/controller.tsx` for nested route maps"). It doesn't need the full explorer registry system from the UI demo, just a simple page map.

### 5. Theme toggle implementation

**Decision**: A `clientEntry` in `app/ui/theme-toggle.tsx` that toggles `data-theme="dark"` on `<html>` and persists the choice to `localStorage` + cookie. The server reads the cookie to render the correct initial theme.

**Rationale**: This matches the bookstore's proven implementation. The client entry approach means no JS framework overhead — just a click handler on the toggle button. The cookie + localStorage combination ensures the theme is correct on first paint (server-rendered) and persists across sessions (client-side).

## Risks / Trade-offs

- **[Risk] Mixin files grow stale if new variants are added but not extracted** → Mitigation: The namespace pattern makes extraction trivial — add a new property to the object. The `button.` autocomplete makes it easy to discover what exists, reducing the incentive to inline.
- **[Risk] Showcase pages duplicate maintenance effort** → Mitigation: The showcase uses the same mixins, primitives, and theme as the rest of the app. If a mixin changes, the showcase reflects it automatically. The pages are ~20 lines each — negligible maintenance.
- **[Risk] Nav registry becomes a dumping ground** → Mitigation: Section grouping and role-based filtering provide structure. The navigation is driven by data, not by adding entries — each entry represents a real page with a route.
- **[Trade-off] Custom theme vs. RMX_01** → Custom theme keeps the starter's identity but misses the RMX_01 glyph sheet and component style contracts. If the starter later adopts `@remix-run/ui` components, it can switch to RMX_01 with no architectural change — only the values file changes.
